## A. 文档体系重构（2026-09-25）

### 现象（重构前的实际状态）

- 仓库根目录堆着 5 个互不相干的 .md：`PROXYAI.md`（既是 AI 守则又是设计大纲）、`PROGRESS.md`、
  `TODO.md`、`MODRINTH.md`、`TRAILER.md`（后两个是分发文案，与工程无关）。
- `PROXYAI.md` 一份文件同时承担：AI 守则（1 条）、设计大纲（§1–11）、实现顺序（§12）、标识符表（§13）。
- `PROGRESS.md` 是 1645 行的**流水账**：章节按 `§13.1 … §13.17` 无限追加，
  同一主题（例如"联机一致性"）散落在 §7.6 / §13.12 / §13.13 / §13.14 四处。
- **两处章节编号碰撞**：两个 `§13.15`、两个 `§13.16`。
- 最关键的：**`.gitignore` 里列着那五个文档**（`MODRINTH.md` / `PROGRESS.md` / `PROXYAI.md` /
  `TRAILER.md` / `TODO.md`），造成一种自相矛盾的状态——其中 `PROXYAI.md`、`PROGRESS.md`、`TRAILER.md`
  其实**早就被跟踪**（先于该规则存在，git 不理会已跟踪文件的 ignore，规则对它们无效，纯属误导），
  而 `MODRINTH.md` 与 `TODO.md` 是后加的，被**静默挡在版本控制之外**——从未提交、外部不可见。
- 后果：`TODO.md`（44KB 的待办清单）一直只存在于本地；看 `.gitignore` 会以为文档完全不受管理；
  基于仓库做审查时拿到的是删掉了关键上下文的信息。
- 另外：每次让 AI "了解项目"都要重新考古 2000+ 行；新讨论出的玩法方向一处都没记。

### 根因

1. **一份文档干两件事**：守则（常驻、必须读）与设计（长、按需读）混在一起，
   于是它既不适合通读也不适合检索。
2. **进度用"追加"而不是"归并"**：新发现新开一节，同一主题越切越碎，教训被埋在流水账里。
3. **`.gitignore` 同时存在"多余"与"致命"两种错误**：
   多余——把已跟踪的文档也列进去（无效但误导，让人以为文档不受管理）；
   致命——后加的文档被静默挡住，不报错、不可见，只有 `git status` 里"不出现"这一个线索。
   两条都源于同一个习惯：**用 ignore 来表达"这个先不收"**，而 ignore 不是为此设计的。
4. **没有规定"什么信息写到哪里"**：待办同时出现在 TODO、设计大纲的"待做"、进度的"未做"里，
   三处会漂移。

## B. 玩法方向讨论（2026-09-25）

> 结论已经写进 [`../DESIGN.md`](../DESIGN.md) §13（玩法设计意图）与 §14（开放取舍），
> 实施条目已经进 [`../BACKLOG.md`](../BACKLOG.md) P2-6。本节只记"讨论是怎么发生的、结论是什么"。

### 现象

对已实现的主线（碎片 → 候选观测者 → 装核心 → 失焦终止）做玩法复盘时发现：
机制都实现了，但**核心体验没有落地**。具体表现为四个可复算的事实：

1. 玩家的动词只有"建造"和"破坏"；"发现规律"这件事游戏里没有任何机制在**产出**它——
   玩家做出假设后，游戏既不确认也不否认。
2. **阶段 1 没有"逐渐"的体感**：累积回扫窗口固定 128 周期（约 21 分钟越过后，
   每个被扫到的方块都必然已命中过至少一次），按 `0.99^N < 1%` 算，
   **约 38 分钟时全图 99% 的方块已非原样**，而阶段 1 持续到第 3 天（约 72 分钟）。
   即"阶段 1 → 2 → 3 逐渐恶化"在画面上根本看不出来。
3. `wild_chance = 0.25` 意味着每四次突变就有一次完全跨语义，而大池自动纳入 598 个方块
   （含装饰方块、含矿物）且等概率 → 玩家看到最多的是"羊毛变成带釉陶瓦"。
   问题不是"太随机"，是**没有意义**——连"不对"都算不上，只是无聊。
4. 主线可绕行：候选体练满 100 点可以不下界、不去末地完成，王座与龙成了可选内容。

### 结论

- **最重要的一条**：项目缺一个动词——**观察产出预测**。
  技术资产（确定性 `resolve`、池结构、`GuidedBias` 的 q）已经具备 90%，
  缺的是把它暴露给玩家：手持模型右键给出"这个概念的成员下一步最可能变成什么，置信度 q"。
  预测本来就该是真的——它是确定性函数的输出，任意周期都能算。
- **恐怖感的来源**不是"不可预测"，而是"读懂了规则、并且知道规则指向什么"。
  因此"让规则可读"与"让世界显得陌生"不冲突；把确定性藏起来才是浪费。
- **资源经济的目标语义**：失焦应该产生**错位**，不该产生**价值**。
  石头变泥土对，石头变钻石矿错。定向生产（概念引导）才是致富路径。
- **安全区该有代价**：要侵蚀的是**稳定性**（护盾会衰减、需要维护），不是"世界"。
- **碎片应该长在信息层上**（成为新的感知维度），而不是当进度点。

### 验证

**未验证**——以上全部是设计判断，尚无实机数据。它们对应的实施条目在 `BACKLOG.md` P2-6，
每条都标了所需的验收方式（多数是 `[实机]` 主观评估 + 一个可自测的断言）。

**唯一可复算的部分**是第 2 条（38 分钟 / 99% 全图失焦）与第 3 条（0.25 × 598 池）：
前者由 `CUMULATIVE_SCAN_CAP = 128`、`block_mutation_chance_stage1 = 0.01`、
`base_interval = 100`、`stage2_day = 3` 直接算出，后者由配置与
`MutationIndexBuilder` 的 `wild_auto_include` 逻辑直接读出。

## C. 锚固化无视既有保护（2026-09-25）

> 对应的 BACKLOG 条目 `P0-2`（已从 BACKLOG 删除，按 `AGENTS.md` §5 移到本节）。
> 顺带把同一函数的**耗时埋点**做了，那是 `P0-1` 的第一步。

### 现象

`convertPrototypeRange`（把保护范围内的方块"固化"成当前失焦态）在解析时硬传
`MutationHelper.Protection.NONE`，也就是把"当前位置是否落在**别的**原型机硬保护范围内"整个忽略了。
代码注释只解释了"为什么忽略**新**登记的那一个效果"，但实现把所有保护都忽略了。

后果：在一个已存在的稳定场内部再放一座基座（或给已有基座换模触发固化），
服务端会把那个场里**本应冻结**的方块按当前失焦态重写；而客户端
（`ClientRegionData#protectionInfo`）仍然认为那里是硬保护、不显示幽灵。
两边对不上，表现为玩家能看见的失配。

### 根因

调用顺序是"**先固化、后登记**"（`updatePrototypeEffect` 在固化之后才调用），
所以固化时 `manager.getPrototypeEffects()` 里只有**其他**既有原型机——这恰好是我们想要的那份名单。
写成"传 `NONE`"不是因为取不到，而是当初只想着"新效果还没登记，所以没有引导"，
顺手把保护也一起传了 `NONE`，没有意识到这一步正是唯一能看见既有保护的时机。

### 修法

1. `MutationEventHandler.convertPrototypeRange` 改为逐坐标先取
   `manager.protectionInfo(p, state, stage)`；**硬保护命中的坐标直接跳过**，
   软保护（阶段 3 语义锁定）按原语义继续参与解析。
2. 函数改为返回 `MutationEventHandler.NormalizeStats(scanned, changed, skippedProtected)`。
   加这个返回值是为了让"保护有没有生效"变成**可观测的数字**——
   原来只能靠"某个方块碰巧变没变"推断，那取决于概率骰子，写不出稳定断言。
3. 新增 `AnchorNormalizeProfiler`：每次固化打一行 INFO（半径 / 遍历坐标数 / 实际扫描 / 实际改写 /
   耗时 / 本线程 CPU 时间 / 吞吐），并累计统计供 `/focaldecay mutation selftest` 末尾打印。
4. 新增 `AnchorNormalizeAudit` → `/focaldecay mutation selftest` 的 `[anchor]` 一行。

### 验证

**已验证（A/B 实跑，无头服务器，devtest 数据包自动触发）**

| 版本 | `[anchor]` 输出 |
|---|---|
| `protectionInfo`（修复） | `PASS scanned=0 changed=0 skippedProtected=1` |
| `Protection.NONE`（旧行为） | `FAIL scanned=1 changed=0 skippedProtected=0` |

断言是确定性的，不依赖概率骰子：外层固化的整个作用域都在内层硬保护之内，所以
`scanned` 必须为 0（没有任何坐标绕过保护进入解析），且 `skippedProtected > 0`
（确实有突变源存在、是被保护拦下的——这一条排除"范围里根本没有源方块"的空跑）。

**这条断言返工过两次，两次都是 A/B 抓出来的**，值得记下来：

1. **第一版是空断言**。直接用现场原有方块当探针，而那片区域（y=102 附近的地下）**全是空气**，
   固化循环连 `isSource` 都判不过去，一个坐标都没解析。
   把缺陷放回去测试照样 PASS。→ 改成自己放一块 `minecraft:stone`。
2. **第二版断言了一个与修复无关的东西**。加了"这块石头跑完必须还是石头"的副断言，
   但内层固化（半径 12）发生在**保护登记之前**，会把它按当前失焦态改写掉
   （实测变成 `pink_wool`）。我曾试图用出生周期闸门保住它，也不成立——
   调试倍率 4 下闸门只维持同一个显示周期，实测 `after place: stone` → `after inner anchor: pink_wool`。
   → 结论：被测性质是"外层固化有没有把既有保护区当成可写区域"，
   该由计数回答，**不该断言任何方块的状态**。

> **A/B 在这条上直接救了场**：两次假通过/假失败都是"把缺陷放回去看它会不会 FAIL"暴露的。
> 这正是 `AGENTS.md` §4 把 A/B 列为硬要求的原因。

| 实际改写 | 1 | **821** |
| 耗时 | 4 ms | **66 ms**（CPU 62 ms） |

**关键读数**：半径 32 的 66 ms **只覆盖已加载的区块**——274,625 个坐标里只有 4,879 个被扫描，
即 1.8%；`isLoaded` 守卫把未加载区域整个跳过了。
所以真实游玩中若目标范围内区块全部加载，耗时按扫描量等比放大到**秒级**是合理外推，
但**这不是实测数字**，需要在"区块全加载"条件下复测（已写进 `BACKLOG.md` P0-1 与 P0-8 矩阵）。

另外 `setBlock` 的开销远大于解析：4,879 次扫描里 821 次真的写了方块，而写入占了大部分时间。
这条指向的优化方向和"减少解析开销"不同——**要省的是写入次数，而不是回扫步数**。

## D. 掉落物突变丢件与丢组件（2026-09-25）

> 对应的 BACKLOG 条目 `P0-3`（已从 BACKLOG 删除，按 `AGENTS.md` §5 移到本节）。
> 同条目里的第三项"随机销毁"（数量守恒地变成贵重物品，等于资源水龙头）属于**玩法取向**，
> 不是缺陷，保留在 `BACKLOG.md` 的 `P2-6d`。

### 现象

`DoomsdayHandler` 的掉落物突变把整堆物品换成一个随机方块物品：

```java
Block[] blockPool = MutationIndexes.get(level.dimension()).wild().flat();
Block block = blockPool[random.nextInt(blockPool.length)];
ItemStack stack = itemEntity.getItem();
itemEntity.setItem(new ItemStack(block.asItem(), stack.getCount()));
```

两个缺陷：

1. **丢件**：不是每个方块都注册了 `BlockItem`，`Block#asItem()` 对它们返回 `Items.AIR`。
   `new ItemStack(AIR, n).isEmpty()` 为真，而原版 `ItemEntity#tick` 对空栈物品实体直接
   `discard()` —— **整堆物品静默消失**，没有任何日志。
2. **丢组件**：`new ItemStack(item, count)` 会丢掉全部数据组件（附魔、命名、耐久、容器内容、模组组件）。

### 根因

抽取用错了池。`wild().flat()` 是**方块**池，而掉落物需要的是**物品**池；
两者之间差着"这个方块有没有对应物品"这一层。这一层在 `wild_auto_include=true` 下不受控——
大池自动纳入"所有 cube 且无方块实体"的方块，其中就包括没有 BlockItem 的那些。

**元凶在原版里就存在**：审计装好后第一次运行就报 `+1 blocks have no item`，
点名后是 **`minecraft:frosted_ice`（霜冰）**——一个原版方块，没有对应物品。
也就是说这个 bug **在纯原版环境下就能真实触发**，命中概率约 1/598；装上模组后池子更大，概率上升。

### 修法

1. `MutationIndex#itemPool()`：在**构建期**从大池过滤出 `asItem() != Items.AIR` 的成员，
   缓存成 `Item[]`（惰性 + `volatile`）。构建期过滤而不是抽取时判断，是为了把"偶发丢件"
   变成**结构上不可能**，并且让审计可以断言这件事。
2. `DoomsdayHandler` 改用物品池，并把 `new ItemStack(item, count)` 换成
   `stack.transmuteCopy(target, stack.getCount())`——保留全部组件，只换物品类型。数量原样保留。
3. `mutation audit` 增加掉落物池审计（条数、排除数、被排除的方块名单）。
4. `mutation selftest` 增加三条断言（见下）。

### 验证

**已验证（A/B 实跑，无头服务器，devtest 数据包自动触发）**

| 版本 | 输出 |
|---|---|
| 过滤在位（修复） | `item pool: 597 items from 598 wild blocks (+1 excluded) OK`；三条 selftest 全 `PASS` |
| 去掉过滤（回归） | `598 items from 598 wild blocks (+0 excluded) FAIL`；`no itemless entry (full scan of 598): FAIL (1 AIR entries)`；`keeps the stack non-empty: FAIL (1 empty results)`；`keeps components: FAIL (1 lost)` |

**断言本身也返工过一次，同样是 A/B 抓出来的**：最初只用"随机抽 256 个目标"来验非空栈，
而池里混进的坏条目只有 1 个——**大概率抽不到，改坏了也会 PASS**。
于是补了一条**全量扫描**断言（`airInPool == 0`，扫全部 597/598 项），它才是真正的回归网。

这条与 §C 是同一个教训的第二次出现：**断言的覆盖范围必须覆盖风险的全部，
不能靠抽样**；而且都要靠"把缺陷放回去"来确认它真的会 FAIL。

**已验证**：`compileJava` 通过；`build -x test` 通过；
`mutation audit`（含新增审计）/ `selftest`（含 `[sync]` 9 项与新增 3 项）/
`throne selftest` / `[anchor]` / devtest A–H 段全部照旧通过，无新增 ERROR。

**未验证（明确区分）**：
- **端到端**（真的让一个 `ItemEntity` 在游戏里被突变、并观察它没消失）没有自动化断言。
  理由：`mutateEntities` 由 tick 驱动且按概率命中，写稳定的集成测试需要给生产代码开测试钩子，
  收益不抵代价。风险的**来源**（池里有没有无物品条目）已被全量断言覆盖，
  而"运行时确实使用了这个池"是读代码确认的单点。
  仍然建议在 `P0-8` 的实机矩阵里加一条观感检查。
- **组件的语义后果**：保留组件意味着"附魔钻石镐变成附魔石头"，这是否是想要的行为**没有拍板**。
  当前实现选了"不丢数据"，最坏结果是产出物有点怪；反过来的选择（只保留数量）会静默销毁数据。
  手册与 `DESIGN.md` 尚未描述这条规则。

## E. 实体突变的身份与安全转换（2026-09-25）

> 对应 BACKLOG 条目 `P1-1`（种子没有实体身份）与 `P1-1c`（先 discard 再建新实体），
> 两条都已从 BACKLOG 删除。它们在同一个函数里，一起修的。

### 现象

1. **同格实体共享命运**。`DoomsdayHandler` 的种子是
   `mix64(worldSeed ^ entity.blockPosition().asLong() ^ tick)`——只用到方块坐标。
   同一 tick、同一方格里的多个实体于是拿到**完全相同的随机序列**：是否突变、突变成什么全都一样。
   牧场里挤在一起的牛羊、刷怪塔里堆叠的怪，会"一群一起变成同一只僵尸"。
2. **转换失败会凭空删生物**。`EntityMutation.convert` 里 `source.discard()` 排在
   `targetType.create(...)` 的空值检查与 `load(...)` **之前**：
   create 返回 null、或 load 抛异常时，**旧实体已经被删、新实体还不存在**。
   load 抛的异常还会直接逃出 tick 处理器。

### 根因

1. 种子只覆盖了"位置 + 时间"，漏掉了"是哪个实体"。`blockPosition()` 是**方块**坐标，
   不是实体身份——这是把方块世界的那套种子公式直接套到实体上的后果
   （方块那边位置就够了，因为一格只有一个方块；实体不是）。
2. `convert` 把"移除旧的"写在了"准备好新的"前面。这类顺序错误在正常路径上看不出来，
   只在失败路径上变成数据丢失。

### 修法

1. 抽出纯函数 `DoomsdayHandler.mutationSeed(worldSeed, pos, tick, entityId)`，
   三个分量**各自先 `mix64` 再异或**——坐标低位、UUID 低位、tick 低位会互相纠缠
   （方块种子那边为这个付过一次学费，见 §5 的纵向随机性修复）。
   调用点改为传 `entity.getUUID()`。
2. `EntityMutation.convert` 调整为：**先 create → 再 load（包 try/catch，失败则丢弃半成品并保留源实体）
   → 最后 discard 源实体 → addFreshEntity**。
   失败时的语义是"转换没发生"，而不是"留下一个空位"（调用方无法区分，但对玩家而言"没变"远好于"没了"）。
   load 失败会打一条 ASCII 日志（含目标类型与异常）。
3. `DoomsdayHandler.selfTest(worldSeed)` → `/focaldecay mutation selftest` 的 `[entity]` 一行。

### 验证

**已验证（A/B 实跑，无头服务器）**

| 版本 | `[entity]` 输出 |
|---|---|
| 含实体身份（修复） | `PASS`（512 个不同实体 → 512 个不同种子） |
| 退回旧公式 | `FAIL (1 distinct - entities sharing a block would mutate identically)` |

`FAIL (1 distinct)` 这个数字把根因钉死了：旧公式下，**无论实体是谁，同位置同 tick 只可能有一个种子**。

断言用**采样分布**（512 个 UUID 要求几乎两两不同）而不是"两个 UUID 给出不同种子"——
后者对单次比较而言是概率性的，写成断言等于碰运气。

**已验证**：`compileJava` 通过；`build -x test` 通过；
`mutation audit` / `selftest`（含 `[sync]` 9 项、`[anchor]`、`[entity]`、item 三条）/
`throne selftest` / devtest A–H 段全部照旧通过，无新增 ERROR。

**未验证**：
- `EntityMutation.convert` 的失败路径没有被自动化断言。`P1-1c` 原计划的验收是
  "用必定失败的转换目标构造一条断言"，实际没做：制造一个 `create==null` 或 `load` 抛异常的
  目标类型需要注册一个病态实体类型，成本明显高于收益，而修复本身是把顺序调整成
  "失败时不改动任何东西"——这是**结构保证**，不依赖运行期验证。若要补，建议放在 `P0-8` 矩阵里
  用一条"转换失败时源实体仍在"的观感检查代替。
- 真实牧场/刷怪塔里的观感（不再整群同步转换）需要 `[实机]`。

### 相关但**未修**的部分（仍在 BACKLOG）

`P1-1b`：实体突变的**范围**没有任何过滤——源是"所有 `Mob`"，所以 Boss（龙/凋灵）、村民、
已驯服生物、命名生物都会被转换；而 `EntityMutation` 的 9 键白名单会丢掉
`Offers`（村民交易）/`HandItems`/`ArmorItems`/`Items`/`NoAI`/乘客/`Silent`。
这一条**没有**在本次一并修，因为它同时涉及机制（过滤规则）与数值（哪些生物豁免），
而且改保留字段策略有回归风险（详见该条目）。种子与顺序这两条是无争议的缺陷，先修了。

## F. 客户端镜像生命周期与两端输入统一（2026-09-25）

> 对应 BACKLOG 的 `P0-5`（同维度重生后镜像永久失效）、`P0-6`（`evaluated` 无界增长）、
> `P0-7`（服务端入口仍读本端配置）。三条同属"客户端镜像与解析输入的生命周期"，一起改的。

### 现象

1. **重生之后客户端再也拿不到保护数据**。区域镜像（原型机保护范围 + 方块诞生周期）由整表快照建立，
   而快照只在**登录**与**换维度**时下发；客户端丢弃镜像的条件却是"{@code ClientLevel} 实例被替换"。
   两件事不重合——**同维度死亡重生**就会换一个 {@code ClientLevel}：镜像被清掉，却没有任何重发路径。
   后果是整局游戏客户端都不知道哪里受保护、哪些方块是玩家放置的：
   在被保护的立方体里照画幽灵（服务端根本不会转换），玩家放置的方块被当成世界原生方块。
2. **`evaluated` 负缓存无界增长**。它在每个编译过的位置被写入，但 `clearCache()` 开头是
   `if (targetCache.isEmpty() && activeSections.isEmpty()) return;`——而"`targetCache` 为空"
   恰恰是 {@code observerOnline = true}（失焦终止、不再产出幽灵）时的常态，断线也走同一路径。
   于是这张表在整个 JVM 会话里单调增长：每个编译过的区块节约 4096 条，键还是装箱的 `Long`。
3. **服务端入口与客户端入口读的不是同一份配置**。{@code MutationTargets.resolveServer} 走"读本端配置"
   的重载（`wild_chance`），`MutationPoolManager.protectionInfo` 读本端 `semantic_lock_stage3_strength`，
   `MutationIndexBuilder` 读本端 `wild_auto_include`；而客户端**只**吃同步下来的快照，
   且 `wild_auto_include` **根本不在快照里**。单人环境两者恰好相同所以从不暴露，
   局域网里客户端改过自己的 toml 就会分叉——与 §13.12 修过的是同一类，只是漏了这三个量。
   另外 `MutationSettings` 只在登录/换维度发，仓库内**没有 `ModConfigEvent` 监听**。

### 根因

三条各自的直接原因不同，但结构性原因是同一个：**"什么会让客户端的镜像/判定失效"这件事，
没有统一的落点**。丢弃判据散在 tick 里（换 level / 换 index / 换周期 / 换快照），
而"失效之后谁来补"只有登录与换维度两条路；配置的取值也散成"服务端读配置、客户端读快照"两条路。

### 修法

**`P0-6` —— 把"要不要重编译"与"要不要丢弃判定"分开**（最小、最直接）：

- `clearCache()` 不再提前 return：清表（`targetCache` / `evaluated` / `activeSections` / `sectionCounts`）
  **无条件做**，只有"标脏重编译"在确实没有幽灵时跳过（那本来就是纯开销）。
- 可以无条件清而不心疼：`clearCache` 的调用点全是低频事件（tick 里的周期/世界/查表变化、
  区域数据与快照更新），不在逐方块路径上；重建判定的代价在下一轮表面扫描里摊开，而那本来就是要做的工作。
- 周期日志加一格 `N cached decisions`（负缓存清空前的条目数），用来盯住这类增长。

**`P0-5` —— 服务端事件与客户端自愈互为兜底**：

- 服务端：新增 `MutationEventHandler.onPlayerRespawn`，**延迟 40 tick** 后补发区域与世界数据。
  延迟是必要的：立即发会被客户端随后的"换 level 清镜像"再清一次，等于白发。
- 客户端：tick 里发现"本维度没有整表快照"就主动请求。新增 C→S 包 `RequestRegionDataPacket`
  （无字段，服务端只回给请求者）。**这条更根本**：它把判据放在"客户端发现自己的数据没了"这个
  **事实**上，而不是"服务端认为客户端该要数据了"这个**推断**上——以后任何新的丢镜像原因都被同一条逻辑覆盖。
  请求前等 20 tick 避开登录时本来就有的那次推送；仍拿不到则每 100 tick 重试并打一条 ASCII 警告。
- `ClientRegionData` 增加显式的**快照标记**（`snapshotReceived`）：不能靠 `byDimension.containsKey`
  代替——`applyPrototype` 在整表到达前就会为维度建一份空数据，于是"键在"不代表"整表到了"。
  标记在 `clear()` 里一起清，否则新世界会以为自己已经收到过快照、**永远不请求重发**。
- **协议版本 1 → 2**：加了包就要改，否则"客户端发一个服务端不认识的包"会以连接失败收场、原因埋在日志里。

**`P0-7` —— 服务端也统一到同一份快照**：

- `MutationSettings` 增加 `wildAutoInclude` 字段并进快照编解码；新增进程级缓存
  `MutationSettings.server(seed)` 与 `invalidateServerCache()`。
- `MutationTargets.resolveServer` 改走快照入口；`MutationPoolManager.protectionInfo` 增加
  `MutationSettings` 参数，语义锁定强度取自快照。
- `MutationIndexBuilder` 不再直接读配置：取值经 `MutationIndexes.wildAutoInclude()`，
  由服务端（`fromConfig`）与客户端（收到快照）各自设置，**变化时丢弃索引缓存**（它决定池成员）。
- 新增 `ModConfigHandler`：配置重载时丢弃服务端缓存、重建一次、把新快照重发给所有在线玩家。
- `MutationHelper` 那个"读本端配置"的重载**保留但标注为只给自测用**——`[sync]` 段需要
  "服务端按配置算一遍"来与"客户端按快照算一遍"逐位比对，那正是这条不变量的回归网。

### 验证

**已验证**：`compileJava` / `build -x test` 通过；`runServer` 正常启动（`Done (1.037s)!`）。
全部自动化自测 **0 FAIL**，含：
- `[sync]` 全部 11 行（快照往返 12 字段、新增的"字段确实被搬运"断言、原型机往返、
  两端入口 960 样本逐位一致、阶段/时钟一致、候选体训练、显示刻回报 3 项、出生周期闸门）
- `[selftest]` 13 行（确定性/不收敛/对称/状态迁移/含水/热路径/物品池 3 项）
- `[anchor]` / `[entity]` / `[ritual]` / `[recipe]` 2 项 / `[period]` 8 项 / `[mutation]` 池审计

**新增断言本身也返工过一次，而且它先抓住了自己**：为了盯住"手写编解码漏搬字段"这个盲区
（漏搬时两端都落到默认值，`equals` 依然成立），我写了一条"翻转 `wild_auto_include`
看线上长度变不变"的断言——它 **FAIL 了**，因为 `writeBoolean` 无论真假都只写 1 字节，长度恒等。
改成"翻转后**解码结果**是否跟着变"才是正确判据。

**未验证**：
- **客户端实机**：`P0-5` 与 `P0-6` 都在客户端侧，需要真人游玩确认。具体要看的：
  死亡重生后站在基地保护区内应**无幽灵**；长时挂机后周期日志里的 `N cached decisions` 应保持有界。
  这两项已进 `P0-8` 的实机矩阵。
- **`P0-7` 的重载路径**：`ModConfigHandler` 需要运行期真的触发一次配置重载才能实测；
  自动化跑里没有触发点，目前只有编译与"不崩在构造期"的验证。
  （顺带记一个坑：`ModConfigEvent` 是 **mod bus** 事件，挂到公共 NeoForge 总线会在
  **模组构造阶段**直接抛异常导致整个模组加载失败——不是"功能不生效"那种温和失败。）
- 协议版本升到 2 之后的**跨版本联机**（新客户端 + 旧服务端）没有实测，预期是被连接期校验挡下。

### 副作用：开发测试世界被改过

`[anchor]` 自测会在执行者附近放两座临时基座、放一块石头探针，并在保护区里做一次固化，
跑完还原被它覆盖的那几格。但**半径 12 的固化会改写范围内所有可突变源方块**，
所以 `run/world` 里测试点附近的地层已经是一片失焦后的材质（实测看到 `pink_wool` 之类）。
这与之前那次 QA 探针的代价同类（见 ARCHIVE 里"洞里 1~3 秒"那节的说明）：
`run/world` 是可再生的开发测试世界，`tools/README.md` 里的世界生成测试本来就要求删掉它重建。
**用户的存档在 `run/saves/`，不受影响。**

后续如果要让这个自测更"干净"，可以给它限制在一个已知为空/可安全改写的区域，

## G. 一批独立小缺陷（2026-09-25）

> 对应 BACKLOG `P1-6` 的 16 个子项，本次处理了 7 项（3/4/5/6/8/9/15）。
> 其余 9 项仍在 BACKLOG 里，逐项标注了未做的原因。

### 现象

七条互相独立、但都属于"平时看不出来、出事时很难查"的类型：

3. `pendingSections`（还要扫哪些区块节）换世界时没清——它只在排空后才重建，
   所以换世界后会真的去扫上一个世界的坐标。
4. `activeSections` 出现**幻影条目**，导致多余的重编译：`incrSection`/`decrSection`
   都是"改计数 → 再改集合"两步，而三处调用者（主线程扫描、编译线程、`clearCache`）会交错。
5. `getPrototypeEffects()` 把内部那张**可变**列表直接交出去，调用方会长期持有它。
6. `syncedEffects`（"客户端现在以为的样子"）只增不减——被爆炸/活塞/`/setblock` 移除的基座
   不走 `BreakEvent`，留下的条目永不清理。
8. `totalStabilityRadius` 在 int 里算三角数，越界的 `copies` 会溢出。
9. `FocalDecayWorldData.partialTicks++` 不 `setDirty()`，崩溃最多丢 20 分钟的游戏日进度。
15. 右键的取消结果可以被**更晚**注册的 `receiveCanceled=true` 监听器翻转，
    而本模组无法察觉（于是原版可能拿旧 blockstate 再跑一遍交互）。

### 根因

七条的根因各不相同，但**第 8 条的根因值得单独说**：它反映了一种"靠下游兜底"的习惯——
`Math.max(PROTOTYPE_RADIUS, lost)` 确实把"半径变负数"这一种后果挡住了，
于是问题看起来已经解决。但半径会被当作**固化循环的边界**使用，
而"下游恰好兜住了"不等于"这里算对了"：换一种输入（或换一个调用点）就会漏出去。

### 修法

3. 换世界与断线时一并清扫描队列。
4. `incrSection`/`decrSection` 的复合更新放进同一个 `synchronized` 块，
   `clearCache` 也拿同一把锁——要的就是"两个集合看到同一个状态"，这是原子块能表达、
   无锁结构很难表达的东西。锁只在低频路径上（周期翻页/换世界/换查表/区域数据更新），
   逐方块路径一次都不会碰。
5. `getPrototypeEffects()` 返回**缓存的不可变视图**，内部改动后置空重建。
   不能每次 `List.copyOf`：`convertPrototypeRange` 会在逐坐标循环里调
   `protectionInfo`/`getGuidedBias`，而那两处要遍历这份列表——27 万次复制不可接受。
6. `syncRemoval` 里顺手 `pruneSyncedEffects()`：把"有效中心集合"与 `syncedEffects` 对账。
   判据是精确的——这张表描述"客户端现在以为的样子"，一个中心只要不在有效列表里就不该在表里。
8. 两层独立防护：算术改用 `long`（不可能溢出），返回值再夹进 `[基础半径, 32]`。
   另外给 `ObserverModelData` 加**规范化构造器**，把 `copies` / `progress` / `bioEnergy` /
   `stabilityStrength` 钳进合法域，列表字段做成不可变副本。
   上限取 1024 而不是"配置里的 `total_stability_max_copies`"：
   配置是**玩法约束**，而这里是**数据合法性约束**，两者不该耦合
   （整合包把玩法上限调到 16 时，这里也不该悄悄改写它读到的值）。
9. 每 tick `setDirty()`。写入成本几乎为零（原版按间隔刷盘），丢一整天进度的代价远大于它。
   **调试时钟刻意仍然不落盘**——那是"忘了 reset 会让世界看起来卡住"的测试档位。
15. 加一条诊断：`setCancellationResult(FAIL)` 之后复查一次，
    发现被改掉就打一条 ASCII 警告（带上位置与两侧的值）。我们无法阻止别的模组这么做，
    但可以把它变成**可诊断**的——整合包里出现双重交互时先看这一行。

### 验证

**已验证**：`compileJava` / `build -x test` 通过；`runServer` 正常启动；
全部自动化自测 **0 FAIL**（含新增的两条）。

新增两条断言钉第 8 条的不变式：
```
[selftest] model data clamps out-of-range inputs (copies/progress/energy/strength/concept): PASS
[selftest] total stability radius stays within [base, 32] for extreme copies: PASS
```

**A/B（去掉钳制，期望 FAIL）**：
```
[selftest] model data clamps out-of-range inputs: FAIL copies=2147483647 progress=-7 energy=-3 strength=5.0
[selftest] total stability radius stays within [base, 32] for extreme copies: PASS   ← 注意这条仍是 PASS
```

第二条**在无钳制时依然 PASS**，这是**预期且值得记录**的：半径那处我加的是独立的
`long` 算术 + 夹取，它不依赖入参钳制。也就是说两层防护各自独立成立——
这正好说明"只修一处"是不够的，而两条断言各自守住一层。

**A/B 过程本身也有一个坑**：第一次尝试用"在精简构造器里提前 `return`"来制造回归，
编译直接报 `精简构造器不得包含返回语句`（Java 的硬限制）。
改用"把四行钳制换成自赋值"才得到有效的回归版本。

**未验证**：
- 第 4 条的并发修法无法用现有自测证明（需要真实的并发压力 + 长时运行）。
  真正的验收是长时挂机后不再出现多余重编译——已进 `P0-8` 矩阵。
- 第 15 条的诊断只有在**装了两个会取消右键的模组**时才会触发，无法在纯净环境验证。
- 第 9 条的收益（崩溃少丢进度）需要真的崩溃一次才能观测，属于"按设计正确"而非"实测正确"。

## H. 保护判定去掉热路径分配（2026-09-25）

> 对应 BACKLOG `P1-3`。本次做了三件（实体白名单的登记期解析、保护规则抽成纯函数、
> 客户端引导模型列表的缓存），**空间索引那一项仍未做**，理由写在 BACKLOG 里。

### 现象

1. **逐实体造字符串**：`DoomsdayHandler.isEntityProtected` 对**每个实体**都
   `BuiltInRegistries.ENTITY_TYPE.getKey(type).toString()`，再拿这个字符串去
   `effect.trainedEntities().contains(id)`——而那是 `List<String>`，命中判定是线性扫。
   这两件事都发生在"每阶段周期对每个实体"的路径上。
2. **逐方块重建列表**：`ClientRegionData.guidedModels()` 被 `ClientRenderCache.resolve` /
   `liveTarget` 在**每个方块**上调用，每次都新建一个 `ArrayList`，
   并对每个引导模型重做一次 `MutationIndexes.tagged(concept)`（字符串哈希查找）。
   而 `resolveGuidedModels()` 的注释写着"每次扫描一个区块节解析一次"——
   **注释与代码不一致**本身也是这条缺陷的一部分：它让"这里很便宜"变成了没人再检查的假设。
3. **重复的半径判定**：`PrototypeEffect` 上没有半径方法，`MutationPoolManager` 里另有一个私有
   `withinRadius(pos, effect)` 助手——同一个规则两份实现。

### 根因

方块那一半早就修过（`Set<Block> trained`，见 §13.7 的三条性能问题），**实体那一半漏了**：
同样是"训练列表 → 判定集合"，只补了方块。另外两件（客户端缓存、重复判定）是
"注释描述了意图、代码没有实现"的积累。

### 修法

1. `PrototypeEffect` 增加 `Set<EntityType<?>> trainedEntities`，由新增的
   `parseTrainedEntities(...)` 在<b>登记期</b>解析一次。非法/已移除的 ID 一律忽略
   （训练期可能记下后来被移除的类型，那种条目就该不生效而不是抛异常）。
2. 判定规则收进 `PrototypeEffect#protectsEntity(EntityType, boolean bioStabilizesEntities)`
   ——一个<b>纯函数</b>。收在这里而不是留在调用方的循环里：判定规则与效果数据是一件事，
   散在调用方意味着"加一种型号就要改一处循环"。
   - 配置开关（`bio_stabilize_entities`）由调用方传入而不是在里面读，方法才与配置无关、可直接测。
   - **它不属于"两端必须一致"那类输入**：实体突变只发生在服务端，客户端不参与这个决策
     （与 `MutationSettings` 里那些会影响失焦<b>解析</b>的量不同）。所以服务端读配置是对的，只是读一次就够。
3. `ClientRegionData` 增加 `regionVersion`（任何写入 +1）与引导模型列表缓存；
   失效判据是**版本 + 维度键两个**。
4. `DoomsdayHandler` 增加"没有基座"的快路径（绝大多数世界在这一条上就返回了），
   半径判定改用 `PrototypeEffect#withinRadius`；删掉 Manager 里的重复助手。

### 验证

**已验证**：`compileJava` / `build -x test` 通过；`runServer` 正常；全部自测 **0 FAIL**。
新增两条断言：
```
[selftest] entity protection rules per model type
           (total / bio on+off / bio drained / lock trained+untrained / guided): PASS
[selftest] prototype radius uses Chebyshev distance (inclusive boundary): PASS
```
保护规则那条逐型号走了一遍，含两个容易写反的边界：生物稳定模型的"能量为 0 即失效"、
语义锁定"只护住被训练的**那几种**实体"。半径那条验的是切比雪夫距离与闭区间边界
（`距 4` 在内、`距 5` 在外、三个轴都吃半径）。

**A/B（把语义锁定改成恒 false，模拟"实体白名单没搬过来"）**：
```
entity protection rules per model type: FAIL
prototype radius uses Chebyshev distance: PASS
```
成立——这条断言确实能抓住"实体那半没接上"。

**未验证**：
- **本次修的是分配与重复，不是复杂度**：`protectionInfo` / `getGuidedBias` 仍然是
  线性扫全部原型机。在基座很少时这没差别，所以"没有回退"这件事我用**断言与行为等价性**来保证，
  而不是用基准数字——原有热路径基准在本次改动前后一致（实测 `chance=1.00` 34 ns /
  `chance=0.01` 151 ns，与本轮之前几次运行的 33~37 ns / 154~155 ns 在运行间波动范围内），
  但**它测的是方块解析，不覆盖这两条路径**。要有数字就得给它们单独加微基准，
  那属于空间索引那一项的工作。
- 客户端缓存的收益无法在无头服务器上量测（需要真实客户端跑扫描）。逻辑正确性靠
  "版本 + 维度"双判据 + `[sync]` 的两端一致性断言间接保证；实机看 `N cached decisions` 日志是否稳定。
- 客户端缓存的失效路径（增量到达 → 版本推进 → 下次查询重建）没有专门的断言。
  它是纯数据流，风险低，但如果将来出现"引导模型改了但预览没变"，先查这里。

## I. 编译线程上的 check-then-act 竞态（2026-09-25）

> 对应 BACKLOG `P1-4`（已从 BACKLOG 删除）。目标只有一件事：
> **让"这次查询属于哪个维度"变成显式数据流，而不是让每个查询各自去全局找一个可变字段。**

### 现象

`ClientRegionData` 的三个查询方法各自这样取维度：

```java
Minecraft mc = Minecraft.getInstance();
if (mc.level == null) return null;
return byDimension.get(mc.level.dimension());   // ← 第二次读 mc.level
```

`hasSnapshotForCurrentLevel()` 与 `guidedModels()` 是同一个形状。这类方法会被**区块编译线程**
（ForkJoinPool worker）调用——`ClientRenderCache.resolve` / `ghostState` / `computeTarget` 链上都会到。
于是主线程在两次读之间换世界或断线时：轻则读到错维度（拿到别的世界的保护数据），
重则第二次读返回 null 直接在 worker 上 NPE。

### 根因

`Minecraft.level` **不是 volatile**，而这三处都在做 `check-then-act`。
更根本的是**数据流方向错了**：调用方明明知道自己在处理哪个世界
（`resolve` 手里就有本次编译那个 `RenderChunkRegion` 的 `ClientLevel`），
却让被调用方回头去全局变量里猜。这正是"全局可变状态 + 隐式依赖"会必然产生的缺陷。

### 修法

1. `ClientRegionData` 的查询全部**接收维度参数**：`protectionInfo` / `isProtected` /
   `blockBirthPeriod` / `guidedModels` / `hasSnapshot`。它不再持有或读取任何全局状态。
2. `ClientRenderCache` 增加 `volatile ResourceKey<Level> currentDimension`，
   在 `tick()` 里随 level 一起发布（换世界时赋值，断线时置 null）。
3. **编译路径更精确**：`resolve()` 把 region/level 的校验**提到最前面**，
   于是 `clientLevel` 成为本次调用钉住的实例——保护查询、挖掘判定、`computeTarget` 内部的
   `protectionInfo` / `blockBirthPeriod` 全用它自己的维度，完全不碰全局字段。
   顺带一个好处：外来世界（`clientLevel != this.level`）在更早的地方就返回了。
4. 扫描路径与交互路径传入 `currentDimension`。

换世界时会有一个 tick 的窗口里 `currentDimension` 还是旧维度——但此刻 `byDimension` 已被清空、
新维度的快照也还没到，两个方向的查询都只会得到"没有数据"，也就是
**"不保护、无幽灵预览"这个安全结果**。这个窗口不引入新的错误状态，只是延迟。

### 验证

**已验证**：`compileJava` / `build -x test` 通过；`runServer` 正常；全部自测 **0 FAIL**
（`[sync]` 12 字段往返、`[selftest]` 含实体保护规则、`[anchor]`、`[entity]`、
`[ritual]`、`[recipe]`、`[period]`、池审计）。全仓扫描确认**没有残留的旧签名调用**。
顺手清掉 `ClientRegionData` 里因本次改动而不再使用的 `Minecraft` import。

**未验证（诚实说明）**：
- **竞态本身没有自动化断言**。它需要"主线程换世界"与"worker 线程查询"精确交错，
  而现有自测都跑在服务端主线程上，构造不出这个交错。
  本次能保证的是<b>结构上不再有 check-then-act</b>——`ClientRegionData` 里已经没有任何
  全局字段读取，`currentDimension` 是 volatile、单次读取。
  真正的验收是长时游玩（反复换维度/重生）不再出现 `ClientRegionData` 相关的
  worker 崩溃或"幽灵画错"——已进 `P0-8` 矩阵。
- 客户端行为（编译产物是否完全一致）没有实机比对。改动是纯数据流重构，
  两端一致性的回归网 `[sync]` 全绿。

### 留下的规矩

`AGENTS.md` §3.3 早就写着"从 worker 线程读主线程字段要一次性拿到（不要 check-then-act）"，
并点名了 `ClientRegionData.current()`。这次把它落实了，同时把**数据流方向**这条也写进守则：
**调用方知道自己处理的是哪个世界，就把维度/世界当参数传下去，不要让被调用方回头猜。**

## J. 开发环境与行尾统一（2026-09-25）

> 这不是缺陷修复，是一次**环境与仓库卫生**的整理。记下来的理由是：
> 本次为此花了真实的时间，而踩的坑都不是"难"，而是"没人写过"。

### 现象

1. **shell 环境变了**：原先只能走 PowerShell（Git Bash 起不来、WSL 无发行版），
   后来 Git Bash 可用（bash 5.3.15，`LANG=C.UTF-8`）。
   守则 §3.1 里那套"只能用 PowerShell + 显式处理 GBK"的写法因此过时。
2. **行尾混杂**：`core.autocrlf=true`，而 `.gitattributes` 只给 `src/generated` 下了 `eol=lf`，
   于是绝大多数文件在检出时被换成 CRLF、提交回 LF。
   多个工具（javac / gradle / git 的 `LF will be replaced by CRLF` 提示）都在刷噪音。

### 根因（行尾部分）

`core.autocrlf=true` 对**没有显式 `eol` 属性**的文件做"检出转 CRLF、提交转 LF"。
仓库里的 blob 一直是 LF（所以提交历史是干净的），但**工作区**是 CRLF。
缺的不是"配置错了"，而是"没给这些扩展名写规则"。

### 修法

1. `.gitattributes` 重写为**扩展名白名单**：
   文本扩展名 + `gradlew` + `.gitignore` + `.gitattributes` → `eol=lf`；
   `gradlew.bat` → `eol=crlf`（LF 会让 cmd 解析出错）；
   `.png`/`.nbt`/`.jar`/`.ogg`/`.zip`/`.dat` → `-text`。
   **刻意不用 `* text=auto`**：它靠"前 8000 字节有没有 NUL"猜，
   而本仓库有 `.nbt` 这种"看着像文本、其实是二进制"的格式，猜错会在行尾转换里改坏文件。
   （已有证据支持这个谨慎：`git diff --cached --stat` 显示重归一化**只动了 `.gitattributes` 一个文件**，
   二进制零改动。）
2. `git add --renormalize .` + 删除工作区文件后 `git checkout -- .`（全部已提交，无丢失风险）。
   结果：**351 LF / 3 CRLF**，剩下的 3 个正是两个 LICENSE（外部文本，不在白名单）
   与 `gradlew.bat`（特意 CRLF）。
3. 守则 §3.1 改写为"Git Bash 首选 + 编码与行尾硬规则表"；§3.3 / §6 / §8 同步更新。
   `PITFALLS.md` §1.4 补上四条坑（见下）。

### 验证

**已验证**：`gradlew.bat` 是 `DOS batch file, ASCII text, with CRLF line terminators`；
`gradlew` 是 `POSIX shell script, UTF-8 text executable`；二进制与 HEAD 无差异；
`git check-attr` 对 `*.java`/`*.md` 报 `eol: lf`、对 `*.png` 报 `text: unset`、对 `gradlew.bat` 报 `eol: crlf`；
行尾归一化后 `compileJava` 与 `build -x test` 均通过。

**未验证**：Windows 上 cmd 双击 `gradlew.bat` 的实际行为（只验证了文件属性正确）。

### 本次踩到的四个坑（都已写进 `PITFALLS.md` §1.4）

1. **`git checkout -- .` 会覆盖未暂存的改动**。我刚写完 `.gitattributes` 就跑了一次它
   （目的只是想刷新工作区），改动被静默冲掉——随后半小时都在查"为什么属性不生效"。
2. **属性是从索引/HEAD 读的**。`.gitattributes` 在工作区改好但没 `git add`，
   `git check-attr` 一律回 `unspecified`。这一条与上一条叠加，造成了最误导的现象：
   文件看起来"已经是新的"，git 却完全看不见它。
3. **嵌套 heredoc 的定界符不能重名**。外层用 `PYEOF`、内层也用 `PYEOF`，
   外层被提前结束，python 报 `unterminated triple-quoted string literal`，
   而 bash 随后又对着半个脚本报语法错——两层的报错都指向错误的地方。
4. **PowerShell 写文件带 BOM**。`Set-Content -Encoding UTF8` 写出 `EF BB BF`，
   javac 报 `非法字符: U+FEFF`。改用 `UTF8Encoding(false)`。

> 值得一提：第 1、2 条合起来正好印证了本项目反复出现的那个模式——
> **"看起来对"不等于"是那样"**。我当时的确"看到了新内容的文件"，
> 但 git 读的是另一个地方。这和之前"测试看起来 PASS 其实是空断言"是同一种错误。

## K. 挖掘路径重构（2026-09-25）

**状态**：已修 + A/B 验证（3 次）；客户端侧与整合包兼容性待实机（并入 `P0-8`）。
**BACKLOG 条目**：`P0-4`（已关闭）、`P1-6` 第 16 条（同源，已关闭）、`P1-6` 第 1、7 条（拍板保留现状）。

### 现象

生存模式挖掉一个已经失焦成别的东西的方块时，掉落**不是**你在看的那一块的掉落。

更深一层：同一件事在很多地方同时不对，而且每次"修好一个"都会冒出新的：

| 原版步骤 | 旧实现 | 玩家能看到的表现 |
|---|---|---|
| `playerWillDestroy` | 缺失 | 蜂巢不激怒、依赖它的模组方块状态不更新 |
| `onDestroyedByPlayer` | 缺失 | 拒绝破坏的方块被强行移除；水logged 方块的水一起消失 |
| `block.destroy` | 缺失 | NeoForge 的方块销毁钩子收不到 |
| `playerDestroy` | 缺失 | **自定义覆写的掉落全失效**——容器里的东西直接没了 |
| `spawnAfterBreak` | 缺失 | 红石矿额外掉落、sculk 等方块专属效果消失 |
| `BlockDropsEvent` | 缺失 | 其他模组改掉落/取消掉落全部失效 |
| `RULE_DOBLOCKDROPS` | 未检查 | 见下面"一条被推翻的判断" |
| `onPlayerDestroyItem` | 缺失 | 工具挖坏瞬间的模组钩子收不到事件 |
| `canHarvestBlock` 门控 | 部分 | 模组方块的自定义覆写被绕过 |
| `BlockEntity` 传给 `getDrops` | 传 `null` | 按方块实体算掉落的方块算错 |

### 根因

**不是"还差几个补调用"，是结构错了。**

旧实现在 `BlockEvent.BreakEvent` 里 `setCanceled(true)`，然后手工复刻原版
`ServerPlayerGameMode#destroyBlock` 的收尾（`setBlock(AIR)` → `Block.getDrops` → 自建 `ItemEntity`
→ `getExpDrop` → `mineBlock` → `awardStat` → `causeFoodExhaustion`）。

这条"手工管线"每补一条边就落后一次：原版加一步、别的模组加一个钩子，我们都得再补一次，
而且**没有办法验证"补全了没有"**——差集只能靠人工比对 NeoForge 补丁。

`BlockEvent.BreakEvent` 的公开 API 只有 `getPlayer()` / `setCanceled(boolean)`，
**改不了"被破坏的是哪个方块"**，而原版在事件触发之前就已经把 `blockstate1` 读进局部变量了。
所以唯一的出路是**动世界**。

### 修法

作者拍板选**推荐方案（重派发）**：只替换"被破坏的是哪个方块"这一个变量，让原版管线跑完。

```
BreakEvent(真实方块) 到达
  ↓ BREAK_REDISPATCHING 已置位？ → 是：什么都不做，让原版继续（这次面对的就是目标）
  ↓ 事件已被更早的监听器取消？ → 是：尊重它，什么都不做
  ↓ 校验锁定（位置 + 维度）→ 不通过：清掉，按原版处理
  ↓ setBlock(pos, targetState, 2)     ← 唯一改动世界的一步
  ↓ 清掉 BreakData                     ← 重派发会再次进入本方法，不清就会重复消费
  ↓ BREAK_REDISPATCHING = true
  ↓     player.gameMode.destroyBlock(pos)   ← 原版管线对着目标跑完整流程
  ↓ BREAK_REDISPATCHING = false
  ↓ event.setCanceled(true)            ← 真实方块那一次作废
```

于是上表**全部自动正确**，而且以后原版或别的模组新加的任何一步也自动正确。

**为什么不能"放进去然后不取消事件"**：原版已经抓着**旧** `blockstate1` 往下走了
（`playerWillDestroy` / `onDestroyedByPlayer` / `playerDestroy` 全用那个旧值），
改了世界也改不了它手里那份引用，结果会是"世界里的方块变了、掉落按旧方块算"——另一种不一致。

**`setBlock` 用 flag 2 而不是右键路径那个 flag 3**：这里紧接着就要把这块拆掉，
flag 3 会让邻块在几微秒内被通知两次（"变成目标"、"变成空气"），对红石之类是可见抖动。
方块形状没变，邻块本来就不需要为"这里换了种方块"重算。

**铜块碎片留在重派发之后单独结算**：那是本模组自己的语义掉落，不属于原版管线，没有管线可挂。

### 顺带修掉的三个 `BreakData` 缺陷

| 缺陷 | 修法 |
|---|---|
| 只校验 `pos`、**不校验维度** | 加 `dimension` 字段。`BlockPos` 只是三个整数，同一组坐标在下界与主世界都会相等 |
| `copyOnDeath()` 让锁定跨死亡存活 | **连序列化器一起删掉**（`ModAttachments` 只留 `builder`）。不可序列化 ⇒ 不落盘；不勾 `copyOnDeath` ⇒ 不跨死亡。两条路径一次性消失，而不是靠破坏时逐个校验去兜 |
| `getPeriodIndex()` 记了但从未读取 | 改为**诊断 + 明确不参与判定**，理由见下 |

**关于第三条，第一版做错了，A/B 推翻了它。** 第一版把"周期翻页"当成拒绝转换的理由
（`LockVerdict.STALE_PERIOD` → 清掉锁定、不转换）。写完之后重新推演语义才发现是反的：

- 锁定的语义是"**玩家看到的是哪个方块**"，它在挖掘开始那一刻定下来。
  玩家看着 A 挖下去就该拿到 A 的掉落——"看得见摸不着"正是这个模组要避免的事；
- 拒绝转换的后果是**静默不回退**：看着 A 挖、拿到 B 的掉落，比"按看到的给"更糟；
- 而且它触发得非常容易：调试时钟拨到高速时（`/focaldecay period speed`），
  一次普通挖掘就能跨过好几个周期。

所以周期现在只用于诊断，两条出口：跨周期时打一行 trace；`/focaldecay mutation at`
把整份锁定（位置 / 维度 / 周期 / 目标）连同当前显示刻一起打出来——
"挖出来的掉落和我看到的不一样"这类问题第一次有了可查的数字。
它不再是死数据，而且这两条出口回答的正是那个问题。

### 测试方块（作者批准注册）

`BreakProbeBlock` + 两个注册项 `focal_decay:break_probe_source` / `break_probe_target`：
无 `BlockItem`、不进创造栏、无配方。**没有 `BlockItem` 有一个我们要的副作用**——
`MutationIndex` 的池按 `asItem() != AIR` 过滤，所以测试方块不会被收进失焦候选、污染玩法
（审计输出里能看到它们出现在 "blocks with no item" 那一行，这是预期）。

探针把"原版调用了哪几个回调"变成整数计数，因为这件事用现成方块只能靠掉落间接推断，判据很脆。

### 验证

**已验证（自动化，`/focaldecay mutation selftest` 的 `[break]` 段，4 条断言全 PASS）**：

```
[break] lock validation (position / dimension; period must NOT invalidate): PASS
[break] vanilla pipeline runs on the VISIBLE TARGET (...): PASS
        [probe willDestroy=1 onDestroyedByPlayer=1 playerDestroy=1 spawnAfterBreak=1 dropsSpawned=1 diamonds=1]
[break] control: bare vanilla destroyBlock on the probe fires every callback: PASS
[break] doTileDrops=false suppresses output: PASS diamonds=0 broken=true viaVanillaPipeline=true
```

**A/B（硬要求，3 次）**：

1. **正常路径**：`[break]` 四条全 PASS。
2. **打开 `AB_OLD_MANUAL_PIPELINE`（把手工管线放回去）**：核心断言 FAIL，
   一次报出 5 个子项（`playerWillDestroy` / `onDestroyedByPlayer` / `playerDestroy` 全为 0，
   掉落也没落在被破坏的那一格）；控制组仍 PASS（它不走这条路径——这正好证明控制组测的是探针本身）。
3. **删掉 `validateLock` 里的维度判断**：首条断言 FAIL
   （`wrong dimension accepted (the P0-4 collateral defect)`）。

`AB_OLD_MANUAL_PIPELINE` 是一个**只有系统属性才能打开**的开关
（`gradlew.bat runServer -Dfocaldecay.abOldBreakPipeline=true`），
它保留旧管线那份代码用于回归。之所以固化成开关而不是每次手工改回来：
手工改容易忘了恢复，而且以后重构时没法重跑。

> ⚠️ **踩到的坑：Gradle 的 `JavaExec` 不把命令行的 `-D` 传给 fork 出来的 JVM。**
> 第一次跑 A/B 时 `-Dfocaldecay.abOldBreakPipeline=true` 完全没生效——测试照常跑完、
> 日志里什么都没有、四条断言全 PASS，看起来像"把 bug 放回去也没事"。
> 修法是必须在 `build.gradle` 的 run 配置里显式转发一次。
> 这个坑的危险之处在于**它的表现和"实现其实是好的"一模一样**。

**A/B 抓出的三个测试缺陷**（都不是被测代码的问题）：

1. **防空跑守卫写得太窄**。`doTileDrops=false` 那条本来用"`playerDestroy` 被调用过"当守卫，
   可那正是被测的性质——旧管线下守卫失败（"pipeline did not run at all"）把真正的判据
   （`diamonds=0`，正确）盖掉了，回归网失去鉴别力。守卫现在只回答"这次破坏到底有没有发生"。
2. **断言之间没清现场**。控制组会破坏目标格，而它后面那条断言假设"目标探针还在原处"。
   第一版只在开头清了一次，正常路径下**碰巧通过**（被测代码恰好把现场恢复成了期望的样子），
   旧管线下才暴露。现在每条断言自己 `resetSite`。
3. **按位置圈范围数掉落是错的**。两格相距 3、搜索半径 3，两个盒子必然重叠，
   于是上一条留下的钻石被下一条数进去（实测 `diamonds=2`）。
   改成"破坏前记 UUID 集合、破坏后取差集"，位置歧义从几何上消失。

**一条被推翻的判断（重要）**：`REVIEW-break-path.md` 说旧实现"未检查
`GameRules.RULE_DOBLOCKDROPS` → `doTileDrops=false` 时照样掉东西"。
**A/B 证明这条判断是错的**：把旧管线放回去，`diamonds` 仍然是 0。
原因是 `Block.getDrops` 内部就走 `popResource`，而 `popResource` 自己门控了该规则
（原版 `Block#popResource(Level,BlockPos,ItemStack)`）。旧实现唯一会绕过它的写法是
自己 `new ItemEntity` + `addFreshEntity`——它没这么写。
所以这条断言现在守的**不是**"旧实现的一个 bug"，而是"重派发跑的确实是原版那个入口"。
审计阶段写下的差集表有一项是推测而非实测，这正是本项目要求"区分代码确认的 / 文档声称的 / 推测的"的原因。

**未验证（并入 `P0-8` 实机矩阵）**：

- 装有机器的模组方块（自定义 `playerDestroy` 覆写）破坏后行为正确；
- 潜影盒 / 箱子破坏后内容物正常溢出；
- 红石矿的额外掉落（`spawnAfterBreak`）；
- 创造模式破坏行为不变；
- **中途放弃挖掘**：方块留在世界里的状态符合预期（这是本方案唯一的可见副作用）；
- **重派发之后原版收尾的幂等性**：`handleBlockBreakAction` 在 `destroyBlock` 返回后
  还会跑自己的收尾（`destroyBlockProgress`、`isDestroyingBlock = false` 等）。
  核对结果是这些大多幂等或会被下次交互覆盖，但**没有实机确认**；
- 可疑方块清单（考古、特殊交互方块）。
- 客户端侧的"方块闪一下"观察：取消事件时原版会把 `state`（真实方块）回发给客户端，
  但世界此刻已是空气、`setBlock` 的更新紧随其后。**理论上不闪，未实测。**
- `/focaldecay mutation at` 新加的 `breakLock=` 那一行，只验证了**无玩家来源**的分支
  （devtest 从控制台跑，打印 `(no player source - run this as a player)`）。
  玩家分支要真人执行才走得到，**未实测**。

## L. 实机验证矩阵与客户端观测性（2026-09-25）

**状态**：矩阵已完成并交付（作者执行）；客户端观测性已补齐并冒烟验证；**矩阵本身大部分行仍未执行**。
**BACKLOG 条目**：`P0-8`（已关闭）、`P1-5` 的观测性部分（条目仍在，优化未做）。

### 现象

`docs/progress/` 里散着十几条明确写着"未做实机验证"的结论。它们的问题不是"没验"，
而是**没法验**：

- 没有一份"要按什么步骤、看哪里、什么算通过"的清单，每次都要重新想一遍；
- 更要命的是**几个关键数字根本观测不到**：
  - `P1-5` 的验收标准原文是"给出某视距下每秒扫描位置数 / 单次扫描耗时"——
    而客户端扫描**一行计时都没有**，只能靠感觉说"大视距下有点卡"；
  - `P0-6`（负缓存无界增长）只有一个间接信号：每 10 分钟一次的周期边界日志。
    想随时看当前 `evaluated` 有多大？做不到。
- `P0-4` 重构刚引入六条只能实机验的兼容性回归，**没有清单就等于没有验收**。

### 根因

不是"忘了写文档"，是**观测点不存在**。写不出可执行步骤，是因为步骤里"看哪里"那一栏填不出来。

所以这一节做两件事：**先补观测点，再写清单**。顺序不能反——
先写清单会写出一堆"观察是否正常"这种没法判定的行。

### 修法

**1. 客户端观测性（作者裁定"加，命令显式打开"）**

| 加了什么 | 在哪 | 为什么是这个形态 |
|---|---|---|
| 四个计数 + 一次计时 | `ClientRenderCache` 的 `scanSections/scanPositions/scanResolves/scanNanos` | 埋点**常开但零日志**：几个 `LongAdder` 自增比被测的那段扫描便宜得多，量具不能比被测物贵；常开是因为"忘了开就量不到"比"多一点开销"糟 |
| 读数与归零 | `/focaldecay clientstats` / `clientstats reset` | 归零后再量一段，才有"改前/改后"的对比 |
| 计时口径 | 复用 `AnchorNormalizeProfiler.cpuClockNanos()` | **不另写一份**：客户端每位置成本与锚固化每位置成本要能直接比，两份实现迟早分叉 |
| 客户端命令注册 | `ClientStatsCommand` + `ClientSetup` 的 `RegisterClientCommandsEvent` | 单独一个**客户端专属类**：它读的是 `ClientRenderCache`（客户端专属），塞进服务端也加载的 `ModCommands` 会在专用服务器上类加载失败（同 §3.5 那条道理） |

`resolves` 单独计数是有意的：`positions` 是"走过多少格"，`resolves` 是"其中多少格真的跑了
≤128 周期回扫"。前者随视距线性涨，后者才决定成本——只有分开记才能看出优化该往哪打。

**2. 实机矩阵**（[`docs/VERIFY-device-matrix.md`](../VERIFY-device-matrix.md)）

- 20 行待验项，每项写清 **前置 / 步骤 / 期望 / 观测点 / 判定**，判定一律是"能截图或能 grep 到某一行"；
- 开头有**共用观测点表**（7 条：`mutation at` 的 `breakLock=`、`trace`、`[sync]` 启动行、`mutation audit`、
  `selftest`、`clientstats`、周期边界日志、锚固化 profiler），后面每项都从这张表里引用；
- 文末**结果登记表**（含"未做"也要写"未做"——留空与"做了且通过"下次读起来看不出区别）；
- 另有一节列出**已经自动化、不要重复手测**的项，避免白做工。

**3. 无人值守的客户端启动验证**（矩阵 §9）

这是本轮唯一能真正自动做掉的部分，也是踩出一条教训的地方，见下。

### 踩到的三个坑

1. **"客户端起得来"不等于"mixin 生效"**（本轮最重要的教训）。
   Mixin 被跳过时游戏照样进得去，只是所有"按可见目标"的行为**静默退回原版**——
   表现是"模组好像没生效"，不崩、不报错、日志里也不一定有痕迹。
   必须显式开 `-Dmixin.debug.verbose=true` 再逐行看 `Mixing …`。
   这条已写进 `AGENTS.md` §4 的客户端那一行——它是"验证清单"里唯一一条**看起来通过了其实没验**的陷阱。
2. **加了方块却忘了资源**。新注册的方块如果 `blockstates/` 与 `models/` 是手写资源（本项目是手写），
   漏掉只会在**客户端**日志里留一行 `missing model for variant: 'focal_decay:…'` 警告，
   服务端、`runData`、`compileJava` **全都不会报**。
   所以"新增方块"的验证清单里必须包含**跑一次客户端看这一行**。
3. **诊断钩子要幂等**。`ScreenEvent.Init.Post` 对 `TitleScreen` 会触发不止一次
   （分辨率变化、返回主菜单都会再来），第一版每次都打，日志里出现两份一模一样的行。
   诊断输出重复比不输出更容易误导——看的人会以为那里真的发生了两次。

### 顺带修掉：`[sync]` 诞生周期闸门断言的**对照物选错了**（这已是第五次）

写这一节的过程中，`[sync] birth gate` 断断续续 FAIL。**根因不是被测代码**，是断言本身：

- 它拿 `storagePeriodIndex` 当"错误的诞生周期"，断言它与真实诞生周期会给出**不同**判定；
- 但回扫从 `birth + 1` 开始、深度上限 `CUMULATIVE_SCAN_CAP = 128`，
  而存储刻算出的周期（实测 952）比显示刻（实测 6664）小得多——
  **两个诞生周期都让回扫一路跑到 128 上限**，判定自然相同；
- 也就是说：那条断言实际测的是"回扫上限有没有生效"，不是"诞生周期有没有用"。
  它在 `speed=0.5` 时碰巧通过（两个周期接近），在 `speed=7` 时必然失败。

**第一次修只修对了一半**：我给每个倍率补上了 `offset = 0`（那时 `run/world` 里残留着
前一段自测设的 `offset=5000`，怀疑是现场不干净）。补上之后仍然 FAIL——
**这才逼出了真正的原因**。这个顺序值得记住：现场不干净是**真实存在的第二个问题**，
但修好它并没有让断言通过，说明还有第三个问题在下面。

改成三条独立断言，各测一件确定的事：

| 断言 | 测什么 | 为什么这样写 |
|---|---|---|
| C：未来诞生 ⇒ 恒定返回原方块 | 闸门会**封住** | `birth = now + 500`，与倍率无关 |
| D：极远的过去 ⇒ 这一刻就变 | 诞生周期**被用作回扫起点** | 若实现忽略该参数，C 与 D 会同时失败 |
| E：显示刻与存储刻给出不同判定 | 诞生周期取的是**显示刻** | 只在倍率 ≠ 1 时才有意义（speed=1 两者相等）；对照物不再是"另一个尺度"，而是"同一次求值换一个诞生周期" |

最终输出带上时钟诊断，于是"这条断言跑在什么时钟状态下"是可见的：

```
[sync] birth gate (...): PASS [speed=1.0 display=964 storage=964 birth=964
                            | speed=7.0 display=6748 storage=964 birth=6748
                            | speed=0.5 display=482 storage=964 birth=482]
```

那三组数字本身就是公式 `floor(gameTick × speed / interval)` 的实测证据
（964 × 7 = 6748、964 × 0.5 = 482）。

### 规律性教训（已提到 `AGENTS.md` §4 与 `PITFALLS.md` §8）

- **"起得来"不是"生效了"**：凡是靠 mixin 注入了行为的功能，验证必须包含"注入本身发生了没有"。
- **观测点不存在时，写不出可执行清单**。验收标准里出现"给出某个数字"这种要求时，
  先确认那个数字**取得出来**；取不出来就先补观测点，别把清单写成"观察是否正常"。
- **差分断言的对照物必须落在"被测差异真的能显现"的范围内**。
  这是本项目第五次由 A/B 或实跑抓出坏断言，而且是一个**新的子类**：
  前四次是"空跑"（断言恒真、抽样不足、守卫盖住判据、现场不干净），
  这一次是"对照物被第三方上限吞掉"——两个输入确实不同，但差异在到达判据之前就被
  `min(…, 128)` 抹平了。**对照物与被测实现共享同一个截断/夹取/上限时，要特别警惕。**

## M. P1-6 第二批：模型数据的两条界限与自测的异常隔离（2026-09-25）

**状态**：三条都已修 + A/B 验证；其中"自测异常隔离"是修的过程中**顺带发现**的问题。
**BACKLOG 条目**：`P1-6` 第 10、13、14 条（已关闭）。

### 现象

三条互不相干的小缺陷，共同点是"改动很小、改错了只有真人玩到才发现"：

1. **副手训练把组件写到主手槽**（第 14 条）。主手训练一切正常；
   换成副手训练时，客户端看到的是**主手那一格被写入了副手那枚模型的组件**。
   表现为"进度显示错位"，真正的副手组件要等下一次整份同步才更新。
2. **候选观测者的记录数没有上限**（第 13 条）。上限判定写的是
   `if (!candidate && current.size() >= limit)`——候选体<b>完全不受</b> `training_max_targets`
   （默认 64）约束，只被 `candidate_required_points` 挡着，而那一项可以配到 10000
   （副本还会把需求除以增益）。结果是一件物品的组件里能塞进**上千个 id 字符串**，
   而 `ObserverModelData` 的 `STREAM_CODEC` 每次记录都要重新序列化整份。
3. **仪式数据不标脏**（第 10 条）。`ThroneRitualData` 的三个 setter 都不调 `setDirty()`，
   靠 `tickRitual` 每 tick 走到下一次标脏兜底。

### 根因

1. 重同步固定写 `serverPlayer.getInventory().selected`，而 `held` 取自
   `event.getEntity().getItemInHand(event.getHand())`。**两者在主手时恰好相同**，
   所以这个 bug 在只看主手时永远不出现。修法是把 `InteractionHand` 一路传下去，
   按手选槽位（副手 = `Inventory.SLOT_OFFHAND`，原版固定槽位 40）。
2. "候选体豁免训练上限"是**有意**的（练满需要超过 64 条记录），
   但"豁免"被写成了"无界"——`!candidate &&` 这个短路把两种情况混成了一种。
   修法是给候选体一个**独立的、仍然宽松但有界的**上限（`candidate_max_targets`，默认 512），
   并在 tooltip 里显示"已记录 N / 上限"——不显示出来，玩家分不清"还差多少练满"
   和"已经到顶了"。
3. 标脏本身很便宜（只置一个 bool，真正的写盘由 SavedData 的保存周期决定），
   不标省不下什么。后果也不严重（丢一拍），但它是**结构性**的隐患：
   任何在两次 tick 之间发生的保存都会写下一份旧值，而"旧值"与"新值"的差别取决于
   崩在什么时刻——这是最难查的那类问题。

### 修法

| 条目 | 改动 |
|---|---|
| 第 14 条 | `addTarget` 增加 `InteractionHand` 参数；新增纯函数 `ModelTrainingHandler#syncSlotFor(ServerPlayer, InteractionHand)`；两个调用点（方块/实体）都把 `event.getHand()` 传下去 |
| 第 13 条 | 新增配置 `candidate_max_targets`（默认 512，范围 1..8192）；上限判定改为按 `candidate` 选不同的上限；候选体 tooltip 显示"已记录 N / 上限"（两个语言文件都补了 key） |
| 第 10 条 | 三个 setter 各补一次 `setDirty()` |

**自测新增 `[model]` 段**（两条断言）：

- 副手槽位：`syncSlotFor(null, OFF_HAND)` 必须等于 `Inventory.SLOT_OFFHAND`。
  **故意传 `null` 是有意的**——副手分支不该解引用 player，所以这个断言同时钉住了
  "返回 40"和"不依赖 player"两件事；
- 候选体上限：`candidate >= training` 且 `<= 8192`。

### 验证

**已验证（自动化，`[model]` 两条 PASS）**：

```
[model] offhand training resyncs the offhand slot, not the selected hotbar slot: PASS
[model] candidate observers have their own bounded record cap (candidate=512, training=64): PASS
```

一轮完整自测：**45 PASS / 0 FAIL**。

**A/B（副手槽位）**：把 `syncSlotFor` 改回恒返回 `player.getInventory().selected`
（即原 bug 的本质）→ 断言以 `NullPointerException` 失败，证明它确实在读这个返回值。

**未验证**：三条都只做了自动化断言与代码路径确认。
"副手训练时客户端显示是否正确""候选体到 512 条之后还能不能继续练""崩服时仪式进度是否保住"
都需要**实机**，已并入矩阵（分别对应 §3 之外的新行，见 §7 登记表说明）。

### 顺带发现：**一段自测抛异常会把后面所有段吞掉**

A/B 那次的结果比"断言 FAIL"糟得多：实现抛 `NullPointerException`，
于是 `selfTestMutation` 里**后面的段一行都没打出来**——
`[selftest]` / `[sync]` 的行数从几十变成 **0**，日志里只有一条孤零零的异常栈。

**为什么这比 FAIL 严重**：自测的价值在于"跑一遍就能信任结论"。一旦某段能炸掉整条命令，
读日志的人会以为"后面那些段没问题"（其实根本没跑），或者以为"命令本身坏了"（其实只是其中一段）。
**"没有输出"和"通过"在肉眼扫日志时长得一模一样。**

修法：命令层把每一段自测包进 try/catch，崩溃的那段打一行能被 grep 到的
`[name] SECTION CRASHED: … FAIL (later sections still run)` + 异常栈，其余段照跑。

**隔离粒度取"每一段"而不是"每一条断言"**：段与段之间本来就不互相依赖（各自准备现场），
而段内部的断言共享现场、单独隔离反而容易掩盖前一条的副作用。

**A/B 验证隔离本身有效**：重新注入同一个 bug →

```
[selftest] SECTION CRASHED: java.lang.NullPointerException: … FAIL (later sections still run)
```

同时 `[anchor]` / `[entity]` / `[break]` 四行**全部照常输出**（对比修之前的 0 行）。

### 规律性教训（已提到 `AGENTS.md` §4 与 `PITFALLS.md` §8）

- **诊断工具必须"失败局部化"**：任何一段能让整条命令静默截断，这个工具就已经在骗人了。
  同理适用于任何"串多个独立检查"的入口。
- **豁免 ≠ 无界**：写 `if (!special && size >= limit)` 时要想清楚
  "那 special 这一类有没有别的界"。短路运算符把两种情况混成一种是非常容易犯的错。
- **"主手恰好等于默认值"会掩盖槽位类 bug**：凡是"默认情况恰好正确"的实现，
  验证必须显式覆盖非默认分支（这里是副手），否则代码看起来是通的。

## N. P1-6 收尾：索引派生缓存的释放与重载后的一致（2026-09-25）

**状态**：两条都已修 + A/B 验证。**`P1-6` 至此清空**（16 项全部处理完）。
**BACKLOG 条目**：`P1-6` 第 11、12 条（已关闭）。

### 现象

两条都只在**数据包重载**这个动作上暴露，而且都不会立刻表现为故障：

1. **`MutationIndex.tagPools` 无淘汰**（第 11 条）：这张表每个条目是一份
   `boolean[registry.size()]`（约 1064 个 bool，一条约 1 KB），而
   `GuidedConcept#fallbackCandidates` 会遍历**每一个**方块标签并逐个调 `tagged(...)`
   ——**一次**概念解析就能把几百个标签全灌进这张表。
   索引本身在重载时被丢弃，但"从缓存里移除"与"回收那几百个数组"之间隔了一整个 GC 周期。
   没有可观测的症状，就是反复重载后内存偏高。
2. **重载后服务端效果持有旧池**（第 12 条）：`PrototypeEffect` 在登记期就把
   `ClassifiedPool` 算好并持有它（热路径要求：逐方块判定不能每次查标签）。
   而 `invalidate()` 丢掉整套索引之后：
   - **客户端**每次从新索引重建（`ClientRegionData` 存的是概念**字符串**、用时才查池）→ 自动是对的；
   - **服务端**手里那份效果还指着**旧池** → 引导邻域两端不一致，
     直到那座原型机被重新登记（取出模型再放回）为止。

   第 2 条是"两端必须逐位一致"这条最高优先级不变量的一个漏洞，比第 1 条严重。

### 根因

第 11 条：`invalidate()` 只做 `CACHE.clear()`，没有给索引一个"释放内部派生缓存"的机会。
第 12 条：**两端存的东西不一样**——客户端存概念字符串（惰性、永远跟当前索引走），
服务端存已解析的池（急切、登记那一刻的快照）。这个不对称本身就是问题所在，
只是在重载之前看不出来。

### 修法

| 条目 | 改动 |
|---|---|
| 第 11 条 | `MutationIndex#releaseCaches()` 清空 `tagPools`；`MutationIndexes#invalidate()` 在 `CACHE.clear()` **之前**遍历所有索引调它。另加 `cachedTagPoolCount()` 让"释放有没有发生"可断言 |
| 第 12 条 | `PrototypeEffect` 加 `dimension` 字段（它本来就按维度分存，只是没记下来）；`updatePrototypeEffect` 登记时写入；新增 `MutationPoolManager#refreshConceptPools()` 用**当前**索引重建所有效果的池；`MutationEventHandler#onTagsUpdated` 里对服务端的每个维度调它 |

**为什么给 `PrototypeEffect` 加维度而不是让调用方去猜**：`MutationPoolManager` 是
`SavedData`，`get(level)` 之后并不保留 level 引用（构造器无参、`load` 也无参），
所以"该取哪个维度的索引"这个信息在重建时是**丢失**的。效果本来就按维度分开存，
把维度记进记录里是最诚实的修法，也比让调用方传一个可能不匹配的维度安全。

**降级行为**：概念标签被数据包删掉时 `conceptPool` 返回 `null`，效果退化成
"半径内但不偏向任何邻域"——正确的降级，不是错误。

### 验证

**已验证（自动化）**：

```
[selftest] tag pool release empties the derived cache and keeps lookups working
           (probe tag minecraft:fence_gates): PASS cached before=2 after=0 lookupOk=true
```

一轮完整自测：**46 PASS / 0 FAIL**，且 `grep -cE '\[(selftest|sync|anchor|entity|break|model|recipe)\]'`
= 42 行（"每一段的输出都在"这件事现在是显式检查的，见 §M）。

**A/B（第 11 条）**：把 `releaseCaches()` 改成空方法体 →
`FAIL cached before=2 after=2`。

**未验证**：

- `refreshConceptPools()` 的**实机效果**——要在有引导模型原型机的情况下
  执行 `/reload`，再确认两端引导邻域一致。**这条没有任何自动化覆盖**
  （它需要真的有一座原型机 + 一次标签重载），已并入矩阵 §5.2 的扩展说明。
- 第 11 条的内存收益没量（本来也没有可观测症状，只有"表清空了"这个事实）。

### 踩到的一个严重的自检错误（已提到 `PITFALLS.md` §1.4）

这一节做完之后，新断言**在日志里一行都不出现**。我按"代码没生效"的方向排查了几轮
（怀疑补丁打错位置、怀疑日志顺序、怀疑断言抛异常），全是错的方向。真实原因是：

> `./gradlew.bat compileJava -q 2>&1 | tail -10 && echo "COMPILE OK"` 里的 `&&`
> 判的是 **`tail` 的退出码**，而 `tail` 永远成功——**编译失败也照样打印 "COMPILE OK"**。

于是我在**四轮工具调用**里一直读着**旧的 `.class`**。真正的错误只是一句
`for (var tag : ...getTagNames())`（它返回 `Stream` 而不是 `Iterable`），
javac 早就报出来了，只是被 `tail` 吃掉了。

最后靠一个与日志无关的手法定位：**比对 `.class` 与 `.java` 的 mtime**，
再用 `javap -p` 看类里有没有新方法名。这比读日志快得多。

**通用规则**（已写进 `PITFALLS.md`）：任何"用管道截断输出"的地方都不要再用 `&&` 判成败；
`grep -c` 在无匹配时返回 **1**，接在 `&&` 后面会把"没有 FAIL 行"变成"命令失败"（也踩过一次）。

### 规律性教训

- **"代码改了但没生效"要先排除"根本没编译"**。查 mtime + `javap`，不要先读日志。
- **两端存的东西不对称时，重载/重建这条路径必然分叉**。
  客户端存字符串（惰性）与服务端存解析结果（急切）都能工作，但它们的**有效期不同**——
  写这类缓存时问一句："它跟着什么失效？"

## O. P1-7 第一半：选择框跟随幽灵（开关，默认关闭）（2026-09-25）

**状态**：已实现 + mixin 织入已验证；**观感未评估**（主观项，需实机）。
**BACKLOG 条目**：`P1-7` 部分完成（选择框那一半），碰撞与射线未做。

### 现象

本模组已经把方块**模型**、面剔除、挖掘速度/工具、中键选取都改成按"可见目标"处理，
但方块选择框（黑框）画的还是**真实方块**的形状。
后果是"看着是半砖、框却框住一整格"——它与"所见即所得"这条取向直接冲突，
而且是玩家最容易察觉的一处，因为准星一直对着它。

### 根因

选择框的形状来自原版 `LevelRenderer#renderLevel` 里这一行：

```java
BlockState blockstate = this.level.getBlockState(blockpos1);
...
this.renderHitOutline(posestack, vertexconsumer2, camera.getEntity(), d0, d1, d2, blockpos1, blockstate);
```

也就是说**在调用 `renderHitOutline` 之前状态就已经查好了**，而
`renderHitOutline` 内部才去取 `state.getShape(...)`——那时已经拿不到"真实方块"了。
所以注入点必须在**上游那一行**，不能改 `renderHitOutline`。

### 修法

- 新增 `LevelRendererOutlineMixin`：重定向那个 `ClientLevel#getBlockState` 调用，
  开关打开时返回 `ClientRenderCache.INSTANCE.visibleState(level, pos)`——
  与渲染、面剔除、挖掘、中键选取**同一个入口**（`MinecraftPickBlockMixin` 也是重定向同一处，
  两处保持同源，将来一起改）。
- 新配置项 `outline_follows_ghost`（客户端，**默认 false**）。关闭时原样返回真实状态，
  于是默认行为与原版**逐位相同**——装了模组但没开开关的人不会看到不一样的选择框。
- **只影响渲染**：不碰碰撞箱、不碰射线命中。

**唯一的 ❌ 是 §3.7**，而且它是个真 bug，见下。

### 根因：两端拿了不同的挖掘硬度

现象：只在"突变让它**变软**"的方块上，方块在客户端消失之后过一小会儿才掉东西。
作者推测"服务端与客户端挖掘时长计算不一致"——**推测完全正确**。

- **客户端** `MultiPlayerGameMode#continueDestroyBlock` 里的 `getDestroyProgress`
  早被 `MultiPlayerGameModeMixin` 重定向到**幽灵**状态（那是"挖掘速度按可见目标"这条既有实现），
  所以进度按幽灵硬度累积，满了就发 `STOP_DESTROY_BLOCK`；
- **服务端** `ServerPlayerGameMode#handleBlockBreakAction` 的 STOP 分支用的是
  `this.level.getBlockState(pos)`（**真实方块**），而且门槛是 **0.7 不是 1.0**：

  ```java
  float f1 = blockstate1.getDestroyProgress(this.player, this.player.level(), pos) * (float)(j + 1);
  if (f1 >= 0.7F) { 真正破坏 } else if (!hasDelayedDestroy) { hasDelayedDestroy = true; ... }
  ```

幽灵更软 → 客户端**早**发停止包 → 服务端按真实（更硬）硬度算不到 0.7 →
掉进 `hasDelayedDestroy` 延迟路径 → **掉落滞后**。
**反向也错**：幽灵更硬时服务端会在客户端还没挖完时就判定破坏。

### 修法

新增 `ServerPlayerGameModeMixin`（挂在**通用** mixin 列表，不是 `client` 列表——
它要跑在专用服务器上），把 `handleBlockBreakAction` 里**全部三处**
`BlockState#getDestroyProgress` 调用一并重定向到
`MutationTargets.resolveServer(level, pos, state)` 的返回值。

- **为什么三处一起改**：起始判定 / STOP 判定 / 延迟破坏路径。只改一处会重现同一类不一致，
  只是换个分支。
- **为什么用 `@Redirect` 而不是把方块换进世界**：这里只是**一次判定**、不是一次操作。
  换方块会真的改世界（那正是破坏路径重构做的，因为那里要跑完整原版管线），
  而这里换完还得换回来，中途的邻块更新、方块实体、别的模组的钩子全要处理——
  代价远大于收益。
- **退回原版的条件**：`resolveServer` 对非转换源、没抽中、观察者在线、受保护的位置
  都返回**原方块**，此时重定向与原版逐位相同。

## R. 实机第三轮：仪式进度被销毁、tooltip 死代码、flaky 断言（2026-09-26）

**状态**：两个真 bug 已修 + A/B；`§3.7` 复验通过；`§4.3` 判据改对后验通；flaky 断言根治。

### 现象与根因

作者按矩阵补跑，给出三条，每一条都是真问题。

#### 一、退出世界即**销毁**仪式进度（比"丢一拍"严重得多）

作者报告："用任务管理器杀进程与正常退出世界**表现相同**，仪式都退回未开始。"

**"表现相同"这个观察直接指向了答案**：如果崩溃与正常退出一样，那就不是崩溃处理的问题，
而是**两者走了同一条分支**。

```java
ServerPlayer player = (ServerPlayer) level.getPlayerByUUID(data.playerId());
if (player == null || !player.isAlive()) { fail(level, data, null); return; }
```

玩家退出世界后就从 level 里消失 → 下一 tick `getPlayerByUUID` 返回 null →
**无条件 `fail`** → `fail` 调 `stop()` → **清空 `playerId`**、`active = false`，然后存盘。

而 `throne_ritual_pause_on_leave`（默认 true）**只管"离开半径"**——
三处判断里唯一漏掉配置的那一处，恰好是会造成数据销毁的那一处。

### 顺带根治：`[sync] birth gate` 是 flaky 的

同一个断言在不同会话里时好时坏（1205 通过 / 1193 失败，且两次都报
"birth=now 与 birth=now-5 给出相同判定"）。

**声明一个偶然成立的东西，它就会 flaky。** 那条断言声明的是
"两个回溯窗口**必定**给出不同判定"——而**那不必然**：累积转换允许两者相同
（k=1 抽中而 k=2..5 都没抽中时，两个窗口给出同一个结果）。

改成声明**必然**成立的那一面，它由回扫窗口的定义直接推出：

```
窗口 = [max(birth + 1, periodIndex - CUMULATIVE_SCAN_CAP + 1), periodIndex]
⇒ 两个诞生周期只要都早于 periodIndex - CAP + 1，就落在同一个有效窗口里，判定必然相同。
```

配合"刚出生的方块在 `now` 冻结"，就得到"诞生周期确实在移动窗口"这个结论——
**与随机种子无关、不 flaky**。连跑三次确认稳定。

### 教训

- **"两种不同操作表现完全相同"是一个强线索**，不是噪声。它说明它们走同一条代码路径，
  于是根因一定在"两者共同经过的地方"，而不是在"两者的差异"里。
  作者那句"任务管理器杀进程也是一样的"直接把我从"崩溃处理"引到了"离线处理"。
- **持久化数据是可以直接读的**。与其猜"到底存了什么"，不如解 NBT 看一句——
  这次正是 `Player` 字段的有无把结论钉死了。
- **声明一个偶然成立的性质，就会得到一条 flaky 的断言**。
  写"必须不同"之前先问：在什么情况下它们**可以**相同？如果答得出来，就别那么断言。

## S. P1-5：客户端扫描优化（增量队列）与它的实测判读（2026-09-26 ~ 09-28）

**状态**：增量队列已实现；mixin 织入已验证（12/12）。
**2026-09-28 实测推翻了本节的验收前提**——`idleShare` 达不到 1.0，而且按现在的数值**不可能**达到；详见文末"2026-09-28 实测"。
**BACKLOG 条目**：`P1-5` 的建议①（已做，做法比原建议更彻底）；建议③未做。

### 现象

§4.6 的实测数字给出了一条明确结论：

```
8 视距:  positions=363,507,712  cpuMs=171,953  nsPerPosition=473.0  queuedSections=503
16 视距: positions=13,180,928   cpuMs=6,187    nsPerPosition=469.4  queuedSections=342
```

- `nsPerPosition` 与视距无关（473 vs 469）→ **每位置的成本没问题**，量具也准；
- 但**扫描器从不空闲**：每 tick 用满 `SCAN_SECTION_BUDGET = 12` 节 = 49,152 位置，
  20 tick/s → 上限 983K/s；实测 8 视距约 **2.11M/s**（平均每次调用跨 2 tick，接近满负荷）。

也就是说它在**持续重扫同一批方块**。这正是 `P1-5` 原文那句
"成本与加载的可见体积成正比、与变化量无关"。

### 根因

`scanSurfaces` 的队列**一空就整体重建**：

```java
if (pendingSections.isEmpty()) {
    rebuildScanQueue(level, mc.player.blockPosition());   // clear() 之后把视野内约 500 个节全部重排
}
```

视距 8 下视野内约 500 节、每次扫 12 节、每 2 tick 扫一次 → 一圈约 42 秒；
但**队列排空之后立刻重建**，所以扫描器永远有活干，而其中绝大多数格子与上次扫描相比
什么都没变。

### 修法：事件驱动的增量队列

把"每轮重扫一切"换成"只在**该扫**的时候扫"。三类入队来源各自的判据：

| 来源 | 什么时候 | 实现在哪 |
|---|---|---|
| **新进入视野** | 相机移动/转头让新的节可见 | `addVisibleSections`，**每 tick 都跑但很便宜**（只做坐标枚举 + 集合查询） |
| **真实方块变了** | 别人挖/放、爆炸、流体 | `onBlockChanged`（由 `ClientLevelSetBlockMixin` 接到 `ClientLevel#setBlock`） |
| **有效期的输入变了** | 周期边界 / 标签变化 / 快照变化 / 换维度 | `clearCache()` 里连队列一起重置 |

三张表分工明确，**不能合并**：
- `queuedSections` = "已经排过队且仍然有效"（判"新的"）；
- `rescansNeeded` = "需要再排一次"（真实方块变了）；
- `visibleLastPass` = "上一轮在视野内"（发现离开视野的节）。

### 三个关键决策及其理由

**① 为什么必须有 `ClientLevel#setBlock` 通知（这是正确性前提，不是优化）**

幽灵是真实方块的函数，而变化只有两种到达方式：玩家自己挖/放（走 `InteractionHandler`），
或者**别人**改的/爆炸/流体改的（客户端只在 `setBlock` 里看到）。

在"从不空闲"的旧实现下，第二种情况会被下一次整体重扫兜住（浪费但正确）。
去掉整体重扫之后**必须**显式通知，否则：

> 别人在我旁边放了一块"会成为突变候选"的方块，而那一节我早扫过了 →
> 它永远不会被重扫 → 那一格不显示幽灵。

注入点选 `ClientLevel#setBlock` 而不是某个包处理器：它是**所有**客户端方块变更的唯一汇聚点，
挂在包处理器上会漏掉本地预测路径。

**② 为什么必须有 `visibleLastPass`（这是我第一版漏掉的）**

"永久记账"这类优化最容易漏的地方是：**记账的有效期必须覆盖所有让它失效的事件**，
而"卸载/重载"是其中之一。

区块离开视野后会被卸载，重新加载时内容**可能已经变了**。如果 `queuedSections`
还记着"这一节扫过了"，它就再也不会被重扫 —— 表现为"走远再回来，那一带的幽灵没了"。

修法：每轮记录视野内的节集合，与上一轮比较，**离开视野的从 `queuedSections` 里忘掉**，
于是它回来时会被当作新节重新排队。

**③ 为什么通知不做任何缓存修改**

`onBlockChanged` 只往并发集合里塞一个 `long`。真正的丢弃交给主线程扫描器
（它本来就会用 `entry.real != real` 把过期条目丢掉）。理由是：立刻丢缓存要改
`targetCache` 与活跃节计数、需要 `sectionLock`，而且会与编译线程抢锁；
而通知可能从网络线程来。**让可能跨线程的入口保持"零副作用"是最省事也最安全的分工。**

### 2026-09-28 实测：`idleShare` 恒为 0，而且它测的是一个不可能的目标

**状态**：本节的前提被实测推翻；**指标要换，代码暂不修**（真优化等 `P2-6a` 拍板周期长度）。

#### 现象

作者的第三次实机（1.0.5）里三行 `[clientstats]` 全部打出来了（上一小节的修复生效），
但 `idleShare=0.00 idleTicks=0`——**静止不动 49 秒也没有一次空闲**：

```
scannedSections=8136 positions=33325056 resolves=1833316 (5.50%) cpuMs=14656 nsPerPosition=439.8
ghostEntries=164056 ghostSections=787 cachedDecisions=2265549 queuedSections=977
P1-5 idleShare=0.00 idleTicks=0 addedByView=16447 rescannedByBlockChange=0
```

#### 根因（两条，一条比一条硬）

1. **账本的寿命比它要摊薄的窗口还短。** 幽灵是周期的函数，周期一变 `clearCache()` 就把
   `queuedSections` 连同全部幽灵一起作废；而 `base_interval=100` → **每 5 秒一个周期**
   （日志里 16 条 `Focal Decay: period …` 正好间隔 5.0 秒）。于是"已经扫过、不用再扫"
   这张表**每 5 秒重建一次**，没有任何东西可以被摊薄。
2. **扫描器是被限流卡住的，不是 CPU 贵。** 静止时视野 ≈505 节，每周期预算 = 12 节 × 50 次 = 600 节
   → 只剩 16% 余量。实测 68 秒扫 8136 节 = **119.6 节/秒**（预算 120，跑满），
   每次调用 **21.6 ms** CPU（主线程 21.6% 常驻）。而一次完整重扫按 CPU 只值 1.1 秒，
   却被摊成 5.18 秒。**"让它停下来"在 5 秒周期下不可能成立**：
   `idleShare` 的上限是 `1 − 505/600 ≈ 0.16`。

顺带查出两个账本隐患（现在被"环"掩盖，修掉环之后会立刻暴露）：

- drain 循环里的 `queuedSections.remove(sectionKey)` 把"已扫过"标记摘掉了 →
  下一轮又被当新节加回来，**每周期白扫 ≈100 节**；
- 重扫通道的入队条件是 `queuedSections.add(key)`，而该表几乎永远包含全部可见节 →
  **"别人改了方块"的通知被静默丢弃**（`rescannedByBlockChange=0`，而 `staleMidPeriod=425`
  证明那 5 秒里真有 425 次真实方块变化）。修法是把一张表拆成"已扫过"与"在队列里"两张。

#### 前瞻

阶段 2/3 的周期是 60/40 tick，预算降到 360/240 节 → **覆盖只有 71% / 47%**，
后期会有整片区块退回真实材质。所以处置顺序是：**先让作者拍板周期语义（`P2-6a`），再决定扫描预算。**

#### 验证

- **已验证**：`idleShare` 这一行确实打得出来了（1.0.5 的修复生效）；
  `scannedSections × 4096 = positions` 逐位吻合（8136 × 4096 = 33,325,056），说明计数器口径正确；
  `debug.log` 里 **12 条** `Mixing … into …` 一条不少（含 `client.ClientLevelSetBlockMixin`），
  所以 `rescannedByBlockChange=0` **不是** mixin 没织入。
- **未验证**：修掉账本隐患后 `idleShare` 能到多少（预计 0.16 封顶）；阶段 3 覆盖率 47% 的实际观感。

两条已提到 `PITFALLS.md` §8：**验收数字先算上限**、**先分清 CPU 贵还是限流紧**。

## U. q 曲线与四个门槛：把"理解了多少"变成"能做什么"（2026-09-29）

**状态**：已实现，`[q]` 段 4 条断言全 PASS，并做过 A/B；**未做客户端实机验证**。
**BACKLOG 条目**：`P2-7` 的第 ② 步。

### 现象

两件事混在一个数里：

1. **曲线的形状**：q 原本是 `coverage × 倍率`（默认 1.0，也就是线性）。线性曲线让前期太慢
   （记录三五个方块毫无手感）、后期太快（最后几十个百分点毫无意义）；
2. **q 只有一个用处**：它只缩放"抽中引导池"的概率，玩家感受不到，也不知道自己练到哪一步了。
   训练过程中更是什么都看不到——只有点"完成训练"那一刻才知道自己练出了什么概念。

### 根因

q 是这套玩法里唯一的"知识"载体（R1「词汇即样本」），却被当成一个内部系数用。
它应该同时是：**一条能学会的曲线**（形状要对）+ **一张分级的能力表**（每一级给一个新动词）。

### 修法

- **上凸曲线** `q = sqrt(已记录 / 需要)`：30 个成员里记录 15 个就是 **70.7%**，
  但 100% 仍然要求记完。于是"早解锁来得快、最后一截很长"：`q ≥ 0.25` 只要 6% 的成员，`q = 1.0` 要 100%。
- **分母的两端补偿**（作者 2026-09-29 点名的两个方向）：
  - **排除没有 `BlockItem` 的成员**：霜冰只能靠冰霜行者获得，留在分母里等于给 `ice` 概念设一个 75% 的天花板；
  - **按 `guided_q_size_cap`（默认 32）封顶**：`ore` 有三十多种成员，否则永远练不满，而主线要用它。
  - 顺带把**分子与分母改成同口径**（都只算"拿得到"的），否则会出现"已记录 4 / 需要 3"这种自相矛盾的显示。
- **四个门槛**（`GuidedConcept.Unlock`）：`0.25 看得见` / `0.50 可以催化` / `0.75 可以行仪式` / `1.00 可以点名目标`。
  判据用**存下来的 q**，不是阶段 3 衰减后的效果 q——衰减砍的是"引导有多灵"，不该把学会的东西收回去。
- **概念可见**：训练过程中每记录一个方块，动作栏报出「已记录 石块 · 概念：原木 43%（6/14）」；
  完成训练时另起一行报明细「已记录 6 / 需要 14（该概念共 16 种）· 解锁：可以催化」；
  **首次练出概念时一次性揭示规则**（"概念由你的样本决定"）——复用 `FocalDecayWorldData` 的位图
  （新增 `BIT_CONCEPT_RULE`，每存档一次；NBT 键名不动，存档兼容）。
- 成品模型的工具提示多一行「解锁：…」：一眼看出这个模型现在能做什么，而不是盯着一个百分比。
- **删掉两个旧配置**：`guided_q_multiplier` / `guided_q_cap`——它们描述的是线性曲线，
  留着就是两条互相矛盾的取值路径（§3.2 的同类问题）。新增 `guided_q_size_cap`。

### 验证

**已验证**（`runServer` 的 `[selftest]`，全 PASS）：

```
[q] convex curve q = sqrt(recorded / required) (half recorded -> 70.7%, all recorded -> 100%, below min trained -> 0): PASS
[q] size cap 32 keeps large concepts completable (ore has 30+ members): PASS
[q] four thresholds, each granting a verb (0.25 see / 0.50 catalyse / 0.75 rite / 1.00 dictate): PASS
[q] untrainable members leave the denominator (minecraft:ice): total=4 trainable=3 -> PASS
```

- **霜冰那条是设计里的例子被机械验证了**：`minecraft:ice` 一共 4 种、可记录 3 种
  （`frosted_ice` 没有 `BlockItem`）。不排除它，这个概念的 q 就永远停在 75%。
- **A/B（把曲线改回线性）**：
  `[q] convex curve … FAIL -> half=0.5 all=1.0 belowMin=0.0`
  —— 断言真的会因为曲线变形而 FAIL，而且失败信息直接打出实际值（0.5 而不是 0.707）。
  这条 A/B 不需要额外开关：断言是**对着手算的 sqrt 期望值**比的，改坏实现就红。

**未验证**：客户端实机（训练过程中的动作栏提示频率是否合适、工具提示那一行是否好读）；
`guided_q_size_cap = 32` 的数值手感。

### 教训

- **"一个数承担两件事"是这类问题的共同形状**：q 既是"练得多好"又是"能做什么"。
  拆开之后才发现曲线形状本身也要按玩法调（上凸/线性/下凸各自对应完全不同的节奏）。
- **断言对着手算的期望值比，A/B 就是免费的**：不需要 test-only 开关，
  改坏实现再跑一次就能看到它红——比"加一个开关再翻转"更省事，也更难自欺。

## V. 催化域：把"变不变"从概率变成必然（2026-09-29）

**状态**：**已全部完成**（解析侧 ③a / 区域管线 ③b-1 / 方块与道具 ③b-2），
`[catalysis]` 段 12 条断言全 PASS；**未做客户端实机验证**。
**BACKLOG 条目**：`P2-7` 的第 ③ 步。

### 现象

引导模型只决定"变成什么"（落点），**不决定"变不变"**。而阶段 1 的每周期命中率是 0.01，
周期长度 5 秒——玩家再怎么引导也看不见效果。他缺的动词不是"我要它变成什么"，
而是"我要它**现在**就变"。这是玩法评审里"触发器"那一条的落点。

### 根因

`resolve` 的两个输入里，"是否发生"（`chance`）来自**全局阶段配置**，"变成什么"（`bias`）来自玩家；
玩家能影响的只有后者，而前者决定了这件事到底会不会被看见。

### 修法（③a：解析侧）

- **新增 `Catalysis`**（`forced` / `wildBonus`），作为 `resolve` 的**显式输入**：
  - `forced` → 该区域每周期命中概率抬到 1（`Catalysis.FORCED_CHANCE`）；
  - `wildBonus` → **域外一圈**的 `wild_chance` 增量，也就是 R2「形可变、量不减」的落点：
    你能决定中心变成什么，但每用一次，周围就多一片你控制不了的变化。
  - 它是**位置相关**的输入，所以不进 `MutationSettings`（那是全局静态快照），
    而是与保护范围、引导模型同源，走**区域效果**那条已同步的通道。
- **保留原 `resolve` 签名**（内部传 `Catalysis.NONE`），新加一个带催化的重载：
  与催化无关的调用方（自测、诊断、旧路径）不必逐个改签名。
- **催化也解锁"跨一级"例外**（P-2 的"引导/催化下"），但 **spill 圈不给**——
  那是无法瞄准的漂移，给它越级等于开一个随机产矿的口子，正是 tier 护栏要堵的东西。
  这条交界写在 `Catalysis` 的类注释里，并有专门的断言守着。

### 修法（③b-1：区域管线）

催化域必须让**两端同时**知道，否则就是"服务端把整片区域点亮、客户端还在按自然概率画"——
玩家看到的世界是安静的，挖下去每块都不一样。这一层刻意复用已有的区域数据套路：

- **`Catalysis.Field`**（中心 / 半径 / 壳厚 / 有效期 / 溢出强度）描述一片域；
  **几何与有效期是两端共用的纯函数**（`Field#at` 与 `Catalysis#at` 合并规则），
  所以"什么时候结束""哪一格算圈里"不需要同步——两端各自拿自己的显示刻算，结论必然相同。
- **不落盘**：一片域只活几十个周期，服务器重启丢掉它是合理的——它不是世界状态，是一次正在发生的事件。
  落盘反而要处理"重启后倒计时怎么算"这种没人关心的问题。
- **增量同步**（`SyncCatalystFieldPacket`，S→C，6 个分量）：与诞生周期同一套路数。
  不塞进整表，是因为域短命而整表只在登录/换维度发——挂在整表上等于"每次点火重发整表"，
  那正是 `P1-6` 第 10 条修掉的毛病。协议版本 `3` → `4`。
- **合并规则与顺序无关**（必中优先、溢出取最大）：服务端按登记顺序遍历、客户端按"整表 + 增量到达顺序"遍历，
  两种顺序不保证一致——与 `betterGuided` 同一条理由。
- 客户端镜像加进 `RegionData`，并且**刻意只留一个三参构造函数**：留一个两参重载的话，
  已有的四处 `new RegionData(...)` 会静默丢掉催化域（"别人动了一下原型机，我的催化域就没了"）。
  让编译器把这些点全部指出来。

### 修法（③b-2：催化剂方块与火种道具）

- **`semantic_catalyst`（语义催化剂）**：插入引导模型 + 火种点火。三件事全走右键，**没有 GUI**：
  插入（手持引导模型右键）/ 取回（潜行空手右键）/ 点火（手持火种）/ 读状态（空手右键一行字）。
  设计原文写的是"界面显示当前区域的概念与 q"——要传的信息本来就只有这一行，
  先由动作栏满足，独立 GUI 留给美术与交互打磨（也避免为它引入 Menu/Screen 与容器同步）。
- **`igniter`（火种）**：消耗**耐久**（64）而不是某种新资源——耐久是玩家已经会读的一条信息。
- **换模型会顺手熄火**：域是"用哪个概念引导"的一次性决定；换了词却继续烧着旧的火，
  玩家会以为新概念已经生效（落点其实还是旧的）。熄火是可见的、可诊断的。
- **点火状态不落盘**（与 `Catalysis.Field` 的理由一致），但**模型落盘**；破坏方块时熄火 + 掉出模型
  （不留一片没有方块驱动的域——那会让客户端一直照着它画）。
- **三个新配置**：`catalyst_duration_periods`(20) / `catalyst_ring_width`(8) / `catalyst_spill_bonus`(0.25)。
  它们只影响**服务端登记那一刻**的取值，之后随 `Field` 一起同步——所以**不进快照**，
  客户端也不需要读到它们就能算出同一个答案（§3.2 的判据是"客户端怎么知道这个值"，答案：它拿到了 Field）。
- 合成有意比原型机便宜（紫水晶块 + 石英块 + 原型）：催化剂是"点火"，应当比"保护"更早拿到，
  否则玩家很长一段时间里只有引信没有火柴。
- 贴图是**程序化生成的占位图**（16×16，脚本在提交信息里可复现），
  刻意与任何原版方块明显不同——直接引用原版贴图（烈焰粉/紫水晶块）会让实机调试时
  分不清"这是模组物品还是原版物品"。找到美术资源后直接替换同名 PNG 即可。

### 验证

**已验证**（`runServer` 的 `[selftest]`，12 条全 PASS）：

最后两条是**登记表的端到端**断言：纯函数自测证明"规则写对了"，它们证明的是**接线对了**——
走真实的 `MutationPoolManager` 登记一片域，再按解析路径的走法去问，答案必须一致；
而且自测必须把自己登记的那片域清掉（它会让附近方块必中，留在世界上等于给开发存档埋一颗雷）。

- **`forced=128` 是精确的"必中"**：用"落点一定不是源方块"的引导池消掉自环之后，
  每个周期都有产出。
- **`plain=10 spill=10` 是精确等式**：命中骰子与"局部/大池"分支用的是同一条随机流，
  spill 只影响后者——所以"改不改是否发生"这件事可以被证否，而不是靠感觉。
- **`spill above T0=0`**：spill 圈里的目标**不得越级**，tier 保证在催化域边界上仍然成立。
- **数据包那条是"逐字段翻转"而不是往返**：`equals` 往返测不出"漏搬一个字段"（两边都落到默认值），
  所以对 6 个字段各造一个"只改它"的变体，解码后必须与原件不同——漏任何一个都会红。

### 实机第二轮：火种"没反应"的真正原因（2026-09-29，1.0.14）

作者第二轮反馈里最关键的是这条：**插入一个 q=75% 的矿物模型并点火，石头底座毫无变化。**
查下来是三层叠在一起，第一层是硬 bug：

1. **插着的模型对落点毫无影响** ✗ bug。`CatalystBlockEntity` 只登记了"必中"（`setCatalystField`），
   **从来没有登记过引导偏向**——火在加速抽奖，但奖池没变。修法：域本身带上概念与 q
   （`Catalysis.Field` 多两个字段 + 数据包多两个分量 + 协议 `4` → `5`），
   两端共用同一个纯函数取偏向（`Catalysis.biasAt` / `Field#biasFor`）。
2. **点火要"点名"，不能沿用背景引导的门控**。原型机的引导只对概念内成员生效
   （"观测雪梨不会让苹果更容易失焦"，原设计如此）；而作者那次实验里石头本来就不是矿物概念的成员，
   所以即使把偏向接上也不会有任何反应。裁定：**域内跳过这道门**——点火是观测者点名。
   （域外的 spill 圈不跳过：那是无法瞄准的漂移。）
3. **只抬档位上限等于没抬**。作者的原话是"这次提升了下次还是按照没提升的抽取，整体还是在下降"——
   那是**结构性**的：逐周期掷骰的升级会被下一次普通命中覆盖。修法两条并行：
   域内档位改为**确定性** `min(源+1, 3)`（火本身就是那次升级的凭据），
   并且把池子换成**"概念 ∩ 恰好那一档"**——"升级了"才真的等于"抽到升级档的方块"。

**点火即写入世界**（作者裁定 #8(b)）：火不再是"只看得见"的窗口，点火那一刻按概念 + q
把半径内结果真的写进世界（与锚固化同一套路数）。于是火第一次**有产出**，
而且写进去的东西不会在火熄灭后恢复。

```
[catalysis] control: the same bias without a lit field never reaches T1 (0/128): PASS

```

- 第一条**逐字复现了作者那次没有反应的实验**（石头底座 + 矿物概念）：点上火之后 128 个样本
  **全部**是 T1 的矿物概念成员，没有一格跑出概念、也没有一格超过 T1。
- 第二条是控制组：同一个偏向**不点火**，0/128 能到 T1 ⇒ 升级来自火，不是来自偏向。

- 协议版本 `4` → `5`（跨版本联机需要两端一致）。

### 实机第三轮：点火期间右键跳变 + 机器不掉落（2026-09-29，1.0.15）

**现象一：点火过程中右键会让方块跳变。** 两个原因叠在一起，一个是我的 bug，一个是语义叠错：

1. **域到达时客户端幽灵没有失效** ✗ bug。`applyCatalystField` 只更新了镜像，
   **忘了让幽灵缓存作废**——而诞生周期那条路径一直有这一步（`dropRegionEntries`）。
   于是客户端还在画点火前的幽灵，服务端已经按域解析：玩家一点右键，"所见即所得"就把他面前的方块
   换成**他没在看的那个**。这是 `PITFALLS` §6.2「缓存的有效期要覆盖全部输入」的又一次实例。
   修法：域到达时丢掉影响范围（半径 + 壳厚）内的幽灵与负缓存，并把这些节标脏重编译。
2. **域内"持续必中"与"点火即写入"是两套语义叠在一起**，而且都有害：
   - **每挖一块再升一档**：写入后的方块仍是源，域内又必中 + 跨级确定 ⇒ 挖走刚写出的铁矿就能拿到 T2。
     一次点火变成一台升级机（这比 BACKLOG 里记的"台阶链"更糟——那至少还要再点一次火）。
   - **整片每周期重抽**：必中意味着每周期都命中，累积语义下每次取"最新那次命中"⇒
     整片每 5 秒换一副样子；而且客户端与服务端的周期相位差（`P2-6i`）被放大成可见的跳变
     （原来 1% 命中时它几乎看不出来）。
   **修法（语义决定）**：点火是**一次性事件**。写入那一刻用显式的 `Catalysis(true, 0)`，
   注册进表里的域此后<b>只带域外那圈 spill</b>——也就是 R2 的代价，而不是额外收益。
   `until` 的含义随之从"必中持续多久"变成"溢出持续多久"。

**现象二：挖掘催化方块只掉模型、不掉方块。** 根因是**漏了战利品表**：
1.21 里方块掉落完全由 `data/<ns>/loot_table/blocks/<id>.json` 决定，**没有那张表就什么都不掉**
（不像旧版本有"掉自己"的兜底）。而本项目的战利品表一律手写（`LootTableProvider` 会静默丢弃
自定义条件键，见 `PITFALLS` §3），于是它成了一张容易被忘掉的手写清单。
**三台可破坏的机器都缺**（催化剂 / 训练终端 / 观测者基座），只是作者先撞上了催化剂。

```
[catalysis] field geometry (nothing inside r=4, spill in the 2-block shell only, nothing beyond;
            verified on the vertical axis too) and expiry at the synced period: PASS
[catalysis] overlapping fields merge order-independently (max spill in the shells; nothing at the centre): PASS
```

### 教训

- **`ClassifiedPool.of(tagId, …)` 的 tagId 会被当成 `ResourceLocation` 解析**：自测里为了区分缓存
  写成 `标签 + "@" + 档位`，第一次跑就崩成 `SECTION CRASHED: Non [a-z0-9/._-] character in path`。
  要区分变体就在**缓存键**上区分。（好消息：段崩溃没有吞掉后面的段——那正是 `[selftest]`
  按段隔离的用处。）
- **"概率提升"与"结果可见"是两件事**：逐周期掷骰的加成会被下一次抽取覆盖，
  这是结构问题，提高概率治不了——只有把加成变成**确定性的**（火本身）或者变成
  **池子的形状**（优先取那一档），玩家才看得见。

### 教训

- **第一版断言算错了基线，被自己的控制组抓住**：我按"1% × 周期数"估"自然命中数"，
  实测却是 **95/128 ≈ 74%**。原因是**累积回扫**——"有没有变"是
  "回看窗口内至少命中过一次"的概率（`1 - 0.99^128`），不是单周期的 1%。
  这与 §Q 那次"断言了一个偶然成立的性质"是同一族：
  **写断言前先把被测量的定义写出来**，别用直觉代替。修法是把判据改成与实测基线比较，
  并加一行说明 `plain` 是累积率——否则下一个人还会误读成"每周期 74%"。
- **消掉自环才能把"必中"钉成等式**：带一个"落点不含源方块"的引导池之后，
  `forced == 采样数` 就是一条精确断言，比"≥ 某个比例"强得多。
- **几何与统计断言要先手算边界，再写**（2026-09-29，本次第三次栽在"断言前提"上）：
  第一版把"r=4 + 壳厚 2"外面那一格写成 `dy=6`（其实 6 还在壳里，7 才是外面），
  又把两个域中心放在 3 格外却指望"同时落在两边的壳里"（那个位置早被其中一片**必中**覆盖了）。
  两次都是**断言的算术错了、实现是对的**。
  防身：把边界值列成一张小表写在断言旁边（`4 / 6 / 7`），算不出来就说明还没想清楚。

## W. 维度大池：`wild_auto_include` 把主世界方块灌进了每一个维度（2026-09-29）

**状态**：已修；`[dim]` 段 3 条断言全 PASS，控制组在同一份日志里给出反证。**非实机验证。**

### 现象

`[dim]` 断言第一次跑起来就 FAIL——下界的大池里有石头、泥土、橡木原木……

```
[focal_decay] mutation index[minecraft:overworld]: wild=600 blocks (+163 auto)
[focal_decay] mutation index[minecraft:the_nether]: wild=600 blocks (+163 auto)   ← 与主世界一模一样
[focal_decay] mutation index[minecraft:the_end]:    wild=600 blocks (+163 auto)
```

### 根因

两件事加在一起：

1. `MutationIndexBuilder` 里的 `wild_auto_include` 分支对**每一个维度**都生效——
   它把"所有 cube 且无方块实体的方块"塞进**该维度**的大池；
2. 而 `wild_auto_include` **默认是开的**。

于是 `poolForDimension` 精心分开的三张大池在默认配置下全部塌回同一张。
**下界与末地的画风保护等于没接。**

### 我为什么会漏掉它

核实 L-1 时我读的是**标签文件**（`wild_nether.json` 45 条全是下界方块、`wild_end.json` 6 条全是末地物），
并据此对作者说"这条**已经做好了**，什么都不用改"。
标签确实是对的——**决定行为的是构建后的池，不是标签本身**。
这条教训已写进 `PITFALLS.md` §12。

### 修法

自动纳入**只对主世界生效**（`wildTag == ModTags.Blocks.MUTATION_POOL_WILD`）：
下界与末地的大池是策展的，尊重策展。

```java
boolean autoInclude = MutationIndexes.wildAutoInclude() && wildTag == ModTags.Blocks.MUTATION_POOL_WILD;
```

一行改动，而且它让"策展标签"这类东西第一次真的拥有权威。

### 验证

**已验证**（`runServer` 的 `[selftest]`）：

```
[dim] nether/end wild pools keep their own palette (44 / 6 blocks, 8 overworld probes): strays=0 / 0 -> PASS
[dim] the three wild pools are built separately (overworld 600): PASS
[dim] control (dimension wiring off, index rebuilt): 8 strays -> PASS (the wiring is what makes the line above true)
```

- **控制组是这一次的关键**：把 `poolForDimension` 假装改回"永远返回主世界大池"并**重建索引**之后，
  下界大池立刻出现 **8 个探针方块**（石头/泥土/草方块/橡木/沙/砾石/圆石/铁矿全中）。
  同一份日志里同时有"修好之后 0 个"与"接线断掉之后 8 个"，所以那条断言不是空的。
- A/B 开关是 `ModTags.Blocks.setIgnoreDimensionForTest(boolean)` + `MutationIndexes.invalidate()`
  （索引是按维度缓存的，翻转开关之后必须重建，否则测的是旧对象——这一点最容易被漏掉）。

**未验证**：实机观感（下界的失焦现在只在下界方块之间打转，是否够"热闹"）。

### 教训

- **验证机制要看"构建后的运行时形态"**：日志里的 `wild=600 (+163 auto)` 一眼就能看出问题，
  而标签文件看不出——因为标签是对的，错的是消费它的那段代码。
- **默认值也是设计的一部分**：这条 bug 的破坏力完全来自"默认开"。
  一个"默认关闭的可选行为"与"默认开启的隐式行为"在文档里长得一样，在世界上完全不同。
