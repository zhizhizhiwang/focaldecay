## A. 文档体系重构（2026-09-25）

### 现象（重构前的实际状态）

- 仓库根目录堆着 5 个互不相干的 .md：`PROXYAI.md`（既是 AI 守则又是设计大纲）、`PROGRESS.md`、
  `TODO.md`、`MODRINTH.md`、`TRAILER.md`（后两个是分发文案，与工程无关）。
- `PROXYAI.md` 一份文件同时承担：AI 守则（1 条）、设计大纲（§1–11）、实现顺序（§12）、标识符表（§13）。
- `PROGRESS.md` 是 1645 行的**流水账**：章节按 `§13.1 … §13.17` 无限追加，
  同一主题（例如"联机一致性"）散落在 §7.6 / §13.12 / §13.13 / §13.14 四处。
- **两处章节编号碰撞**：两个 `§13.15`、两个 `§13.16`。
- 最关键的：**`.gitignore` 里列着那五个文档**（`MODRINTH.md` / `PROGRESS.md` / `PROXYAI.md` /
  `TRAILER.md` / `TODO.md`），造成一种自相矛盾的状态——其中 `PROXYAI.md`、`PROGRESS.md`、`TRAILER.md`
  其实**早就被跟踪**（先于该规则存在，git 不理会已跟踪文件的 ignore，规则对它们无效，纯属误导），
  而 `MODRINTH.md` 与 `TODO.md` 是后加的，被**静默挡在版本控制之外**——从未提交、外部不可见。
- 后果：`TODO.md`（44KB 的待办清单）一直只存在于本地；看 `.gitignore` 会以为文档完全不受管理；
  基于仓库做审查时拿到的是删掉了关键上下文的信息。
- 另外：每次让 AI "了解项目"都要重新考古 2000+ 行；新讨论出的玩法方向一处都没记。

### 根因

1. **一份文档干两件事**：守则（常驻、必须读）与设计（长、按需读）混在一起，
   于是它既不适合通读也不适合检索。
2. **进度用"追加"而不是"归并"**：新发现新开一节，同一主题越切越碎，教训被埋在流水账里。
3. **`.gitignore` 同时存在"多余"与"致命"两种错误**：
   多余——把已跟踪的文档也列进去（无效但误导，让人以为文档不受管理）；
   致命——后加的文档被静默挡住，不报错、不可见，只有 `git status` 里"不出现"这一个线索。
   两条都源于同一个习惯：**用 ignore 来表达"这个先不收"**，而 ignore 不是为此设计的。
4. **没有规定"什么信息写到哪里"**：待办同时出现在 TODO、设计大纲的"待做"、进度的"未做"里，
   三处会漂移。

## B. 玩法方向讨论（2026-09-25）

> 结论已经写进 [`../DESIGN.md`](../DESIGN.md) §13（玩法设计意图）与 §14（开放取舍），
> 实施条目已经进 [`../BACKLOG.md`](../BACKLOG.md) P2-6。本节只记"讨论是怎么发生的、结论是什么"。

### 现象

对已实现的主线（碎片 → 候选观测者 → 装核心 → 失焦终止）做玩法复盘时发现：
机制都实现了，但**核心体验没有落地**。具体表现为四个可复算的事实：

1. 玩家的动词只有"建造"和"破坏"；"发现规律"这件事游戏里没有任何机制在**产出**它——
   玩家做出假设后，游戏既不确认也不否认。
2. **阶段 1 没有"逐渐"的体感**：累积回扫窗口固定 128 周期（约 21 分钟越过后，
   每个被扫到的方块都必然已命中过至少一次），按 `0.99^N < 1%` 算，
   **约 38 分钟时全图 99% 的方块已非原样**，而阶段 1 持续到第 3 天（约 72 分钟）。
   即"阶段 1 → 2 → 3 逐渐恶化"在画面上根本看不出来。
3. `wild_chance = 0.25` 意味着每四次突变就有一次完全跨语义，而大池自动纳入 598 个方块
   （含装饰方块、含矿物）且等概率 → 玩家看到最多的是"羊毛变成带釉陶瓦"。
   问题不是"太随机"，是**没有意义**——连"不对"都算不上，只是无聊。
4. 主线可绕行：候选体练满 100 点可以不下界、不去末地完成，王座与龙成了可选内容。

### 结论

- **最重要的一条**：项目缺一个动词——**观察产出预测**。
  技术资产（确定性 `resolve`、池结构、`GuidedBias` 的 q）已经具备 90%，
  缺的是把它暴露给玩家：手持模型右键给出"这个概念的成员下一步最可能变成什么，置信度 q"。
  预测本来就该是真的——它是确定性函数的输出，任意周期都能算。
- **恐怖感的来源**不是"不可预测"，而是"读懂了规则、并且知道规则指向什么"。
  因此"让规则可读"与"让世界显得陌生"不冲突；把确定性藏起来才是浪费。
- **资源经济的目标语义**：失焦应该产生**错位**，不该产生**价值**。
  石头变泥土对，石头变钻石矿错。定向生产（概念引导）才是致富路径。
- **安全区该有代价**：要侵蚀的是**稳定性**（护盾会衰减、需要维护），不是"世界"。
- **碎片应该长在信息层上**（成为新的感知维度），而不是当进度点。

### 验证

**未验证**——以上全部是设计判断，尚无实机数据。它们对应的实施条目在 `BACKLOG.md` P2-6，
每条都标了所需的验收方式（多数是 `[实机]` 主观评估 + 一个可自测的断言）。

**唯一可复算的部分**是第 2 条（38 分钟 / 99% 全图失焦）与第 3 条（0.25 × 598 池）：
前者由 `CUMULATIVE_SCAN_CAP = 128`、`block_mutation_chance_stage1 = 0.01`、
`base_interval = 100`、`stage2_day = 3` 直接算出，后者由配置与
`MutationIndexBuilder` 的 `wild_auto_include` 逻辑直接读出。

## C. 锚固化无视既有保护（2026-09-25）

> 对应的 BACKLOG 条目 `P0-2`（已从 BACKLOG 删除，按 `AGENTS.md` §5 移到本节）。
> 顺带把同一函数的**耗时埋点**做了，那是 `P0-1` 的第一步。

### 现象

`convertPrototypeRange`（把保护范围内的方块"固化"成当前失焦态）在解析时硬传
`MutationHelper.Protection.NONE`，也就是把"当前位置是否落在**别的**原型机硬保护范围内"整个忽略了。
代码注释只解释了"为什么忽略**新**登记的那一个效果"，但实现把所有保护都忽略了。

后果：在一个已存在的稳定场内部再放一座基座（或给已有基座换模触发固化），
服务端会把那个场里**本应冻结**的方块按当前失焦态重写；而客户端
（`ClientRegionData#protectionInfo`）仍然认为那里是硬保护、不显示幽灵。
两边对不上，表现为玩家能看见的失配。

### 根因

调用顺序是"**先固化、后登记**"（`updatePrototypeEffect` 在固化之后才调用），
所以固化时 `manager.getPrototypeEffects()` 里只有**其他**既有原型机——这恰好是我们想要的那份名单。
写成"传 `NONE`"不是因为取不到，而是当初只想着"新效果还没登记，所以没有引导"，
顺手把保护也一起传了 `NONE`，没有意识到这一步正是唯一能看见既有保护的时机。

### 修法

1. `MutationEventHandler.convertPrototypeRange` 改为逐坐标先取
   `manager.protectionInfo(p, state, stage)`；**硬保护命中的坐标直接跳过**，
   软保护（阶段 3 语义锁定）按原语义继续参与解析。
2. 函数改为返回 `MutationEventHandler.NormalizeStats(scanned, changed, skippedProtected)`。
   加这个返回值是为了让"保护有没有生效"变成**可观测的数字**——
   原来只能靠"某个方块碰巧变没变"推断，那取决于概率骰子，写不出稳定断言。
3. 新增 `AnchorNormalizeProfiler`：每次固化打一行 INFO（半径 / 遍历坐标数 / 实际扫描 / 实际改写 /
   耗时 / 本线程 CPU 时间 / 吞吐），并累计统计供 `/focaldecay mutation selftest` 末尾打印。
4. 新增 `AnchorNormalizeAudit` → `/focaldecay mutation selftest` 的 `[anchor]` 一行。

### 验证

**已验证（A/B 实跑，无头服务器，devtest 数据包自动触发）**

| 版本 | `[anchor]` 输出 |
|---|---|
| `protectionInfo`（修复） | `PASS scanned=0 changed=0 skippedProtected=1` |
| `Protection.NONE`（旧行为） | `FAIL scanned=1 changed=0 skippedProtected=0` |

断言是确定性的，不依赖概率骰子：外层固化的整个作用域都在内层硬保护之内，所以
`scanned` 必须为 0（没有任何坐标绕过保护进入解析），且 `skippedProtected > 0`
（确实有突变源存在、是被保护拦下的——这一条排除"范围里根本没有源方块"的空跑）。

**这条断言返工过两次，两次都是 A/B 抓出来的**，值得记下来：

1. **第一版是空断言**。直接用现场原有方块当探针，而那片区域（y=102 附近的地下）**全是空气**，
   固化循环连 `isSource` 都判不过去，一个坐标都没解析。
   把缺陷放回去测试照样 PASS。→ 改成自己放一块 `minecraft:stone`。
2. **第二版断言了一个与修复无关的东西**。加了"这块石头跑完必须还是石头"的副断言，
   但内层固化（半径 12）发生在**保护登记之前**，会把它按当前失焦态改写掉
   （实测变成 `pink_wool`）。我曾试图用出生周期闸门保住它，也不成立——
   调试倍率 4 下闸门只维持同一个显示周期，实测 `after place: stone` → `after inner anchor: pink_wool`。
   → 结论：被测性质是"外层固化有没有把既有保护区当成可写区域"，
   该由计数回答，**不该断言任何方块的状态**。

> **A/B 在这条上直接救了场**：两次假通过/假失败都是"把缺陷放回去看它会不会 FAIL"暴露的。
> 这正是 `AGENTS.md` §4 把 A/B 列为硬要求的原因。

**已验证**：`compileJava` 通过；`build -x test` 通过；
`mutation audit` / `selftest`（含 `[sync]` 全部 9 项）/ `throne selftest` / devtest A–H 段全部照旧通过，

### 顺带得到的数字（`P0-1` 的第一步）

埋点装好后第一次量到真实数据（无头服务器，devtest 的 `throne selftest` 触发一次半径 32 固化）：

| 项 | 半径 12 | 半径 32 |
|---|---|---|
| 遍历坐标数 | 15,625 | 274,625 |
| 实际扫描 | 1 | **4,879** |
| 实际改写 | 1 | **821** |
| 耗时 | 4 ms | **66 ms**（CPU 62 ms） |

**关键读数**：半径 32 的 66 ms **只覆盖已加载的区块**——274,625 个坐标里只有 4,879 个被扫描，
即 1.8%；`isLoaded` 守卫把未加载区域整个跳过了。
所以真实游玩中若目标范围内区块全部加载，耗时按扫描量等比放大到**秒级**是合理外推，
但**这不是实测数字**，需要在"区块全加载"条件下复测（已写进 `BACKLOG.md` P0-1 与 P0-8 矩阵）。

另外 `setBlock` 的开销远大于解析：4,879 次扫描里 821 次真的写了方块，而写入占了大部分时间。
这条指向的优化方向和"减少解析开销"不同——**要省的是写入次数，而不是回扫步数**。

## D. 掉落物突变丢件与丢组件（2026-09-25）

> 对应的 BACKLOG 条目 `P0-3`（已从 BACKLOG 删除，按 `AGENTS.md` §5 移到本节）。
> 同条目里的第三项"随机销毁"（数量守恒地变成贵重物品，等于资源水龙头）属于**玩法取向**，
> 不是缺陷，保留在 `BACKLOG.md` 的 `P2-6d`。

### 现象

`DoomsdayHandler` 的掉落物突变把整堆物品换成一个随机方块物品：

```java
Block[] blockPool = MutationIndexes.get(level.dimension()).wild().flat();
Block block = blockPool[random.nextInt(blockPool.length)];
ItemStack stack = itemEntity.getItem();
itemEntity.setItem(new ItemStack(block.asItem(), stack.getCount()));
```

两个缺陷：

1. **丢件**：不是每个方块都注册了 `BlockItem`，`Block#asItem()` 对它们返回 `Items.AIR`。
   `new ItemStack(AIR, n).isEmpty()` 为真，而原版 `ItemEntity#tick` 对空栈物品实体直接
   `discard()` —— **整堆物品静默消失**，没有任何日志。
2. **丢组件**：`new ItemStack(item, count)` 会丢掉全部数据组件（附魔、命名、耐久、容器内容、模组组件）。

### 根因

抽取用错了池。`wild().flat()` 是**方块**池，而掉落物需要的是**物品**池；
两者之间差着"这个方块有没有对应物品"这一层。这一层在 `wild_auto_include=true` 下不受控——
大池自动纳入"所有 cube 且无方块实体"的方块，其中就包括没有 BlockItem 的那些。

**元凶在原版里就存在**：审计装好后第一次运行就报 `+1 blocks have no item`，
点名后是 **`minecraft:frosted_ice`（霜冰）**——一个原版方块，没有对应物品。
也就是说这个 bug **在纯原版环境下就能真实触发**，命中概率约 1/598；装上模组后池子更大，概率上升。

### 修法

1. `MutationIndex#itemPool()`：在**构建期**从大池过滤出 `asItem() != Items.AIR` 的成员，
   缓存成 `Item[]`（惰性 + `volatile`）。构建期过滤而不是抽取时判断，是为了把"偶发丢件"
   变成**结构上不可能**，并且让审计可以断言这件事。
2. `DoomsdayHandler` 改用物品池，并把 `new ItemStack(item, count)` 换成
   `stack.transmuteCopy(target, stack.getCount())`——保留全部组件，只换物品类型。数量原样保留。
3. `mutation audit` 增加掉落物池审计（条数、排除数、被排除的方块名单）。
4. `mutation selftest` 增加三条断言（见下）。

### 验证

**已验证（A/B 实跑，无头服务器，devtest 数据包自动触发）**

| 版本 | 输出 |
|---|---|
| 过滤在位（修复） | `item pool: 597 items from 598 wild blocks (+1 excluded) OK`；三条 selftest 全 `PASS` |
| 去掉过滤（回归） | `598 items from 598 wild blocks (+0 excluded) FAIL`；`no itemless entry (full scan of 598): FAIL (1 AIR entries)`；`keeps the stack non-empty: FAIL (1 empty results)`；`keeps components: FAIL (1 lost)` |

**断言本身也返工过一次，同样是 A/B 抓出来的**：最初只用"随机抽 256 个目标"来验非空栈，
而池里混进的坏条目只有 1 个——**大概率抽不到，改坏了也会 PASS**。
于是补了一条**全量扫描**断言（`airInPool == 0`，扫全部 597/598 项），它才是真正的回归网。

这条与 §C 是同一个教训的第二次出现：**断言的覆盖范围必须覆盖风险的全部，
不能靠抽样**；而且都要靠"把缺陷放回去"来确认它真的会 FAIL。

**已验证**：`compileJava` 通过；`build -x test` 通过；
`mutation audit`（含新增审计）/ `selftest`（含 `[sync]` 9 项与新增 3 项）/
`throne selftest` / `[anchor]` / devtest A–H 段全部照旧通过，无新增 ERROR。

**未验证（明确区分）**：
- **端到端**（真的让一个 `ItemEntity` 在游戏里被突变、并观察它没消失）没有自动化断言。
  理由：`mutateEntities` 由 tick 驱动且按概率命中，写稳定的集成测试需要给生产代码开测试钩子，
  收益不抵代价。风险的**来源**（池里有没有无物品条目）已被全量断言覆盖，
  而"运行时确实使用了这个池"是读代码确认的单点。
  仍然建议在 `P0-8` 的实机矩阵里加一条观感检查。
- **组件的语义后果**：保留组件意味着"附魔钻石镐变成附魔石头"，这是否是想要的行为**没有拍板**。
  当前实现选了"不丢数据"，最坏结果是产出物有点怪；反过来的选择（只保留数量）会静默销毁数据。
  手册与 `DESIGN.md` 尚未描述这条规则。

## E. 实体突变的身份与安全转换（2026-09-25）

> 对应 BACKLOG 条目 `P1-1`（种子没有实体身份）与 `P1-1c`（先 discard 再建新实体），
> 两条都已从 BACKLOG 删除。它们在同一个函数里，一起修的。

### 现象

1. **同格实体共享命运**。`DoomsdayHandler` 的种子是
   `mix64(worldSeed ^ entity.blockPosition().asLong() ^ tick)`——只用到方块坐标。
   同一 tick、同一方格里的多个实体于是拿到**完全相同的随机序列**：是否突变、突变成什么全都一样。
   牧场里挤在一起的牛羊、刷怪塔里堆叠的怪，会"一群一起变成同一只僵尸"。
2. **转换失败会凭空删生物**。`EntityMutation.convert` 里 `source.discard()` 排在
   `targetType.create(...)` 的空值检查与 `load(...)` **之前**：
   create 返回 null、或 load 抛异常时，**旧实体已经被删、新实体还不存在**。
   load 抛的异常还会直接逃出 tick 处理器。

### 根因

1. 种子只覆盖了"位置 + 时间"，漏掉了"是哪个实体"。`blockPosition()` 是**方块**坐标，
   不是实体身份——这是把方块世界的那套种子公式直接套到实体上的后果
   （方块那边位置就够了，因为一格只有一个方块；实体不是）。
2. `convert` 把"移除旧的"写在了"准备好新的"前面。这类顺序错误在正常路径上看不出来，
   只在失败路径上变成数据丢失。

### 修法

1. 抽出纯函数 `DoomsdayHandler.mutationSeed(worldSeed, pos, tick, entityId)`，
   三个分量**各自先 `mix64` 再异或**——坐标低位、UUID 低位、tick 低位会互相纠缠
   （方块种子那边为这个付过一次学费，见 §5 的纵向随机性修复）。
   调用点改为传 `entity.getUUID()`。
2. `EntityMutation.convert` 调整为：**先 create → 再 load（包 try/catch，失败则丢弃半成品并保留源实体）
   → 最后 discard 源实体 → addFreshEntity**。
   失败时的语义是"转换没发生"，而不是"留下一个空位"（调用方无法区分，但对玩家而言"没变"远好于"没了"）。
   load 失败会打一条 ASCII 日志（含目标类型与异常）。
3. `DoomsdayHandler.selfTest(worldSeed)` → `/focaldecay mutation selftest` 的 `[entity]` 一行。

### 验证

**已验证（A/B 实跑，无头服务器）**

| 版本 | `[entity]` 输出 |
|---|---|
| 含实体身份（修复） | `PASS`（512 个不同实体 → 512 个不同种子） |
| 退回旧公式 | `FAIL (1 distinct - entities sharing a block would mutate identically)` |

`FAIL (1 distinct)` 这个数字把根因钉死了：旧公式下，**无论实体是谁，同位置同 tick 只可能有一个种子**。

断言用**采样分布**（512 个 UUID 要求几乎两两不同）而不是"两个 UUID 给出不同种子"——
后者对单次比较而言是概率性的，写成断言等于碰运气。

**已验证**：`compileJava` 通过；`build -x test` 通过；
`mutation audit` / `selftest`（含 `[sync]` 9 项、`[anchor]`、`[entity]`、item 三条）/
`throne selftest` / devtest A–H 段全部照旧通过，无新增 ERROR。

**未验证**：
- `EntityMutation.convert` 的失败路径没有被自动化断言。`P1-1c` 原计划的验收是
  "用必定失败的转换目标构造一条断言"，实际没做：制造一个 `create==null` 或 `load` 抛异常的
  目标类型需要注册一个病态实体类型，成本明显高于收益，而修复本身是把顺序调整成
  "失败时不改动任何东西"——这是**结构保证**，不依赖运行期验证。若要补，建议放在 `P0-8` 矩阵里
  用一条"转换失败时源实体仍在"的观感检查代替。
- 真实牧场/刷怪塔里的观感（不再整群同步转换）需要 `[实机]`。

### 相关但**未修**的部分（仍在 BACKLOG）

`P1-1b`：实体突变的**范围**没有任何过滤——源是"所有 `Mob`"，所以 Boss（龙/凋灵）、村民、
已驯服生物、命名生物都会被转换；而 `EntityMutation` 的 9 键白名单会丢掉
`Offers`（村民交易）/`HandItems`/`ArmorItems`/`Items`/`NoAI`/乘客/`Silent`。
这一条**没有**在本次一并修，因为它同时涉及机制（过滤规则）与数值（哪些生物豁免），
而且改保留字段策略有回归风险（详见该条目）。种子与顺序这两条是无争议的缺陷，先修了。

## F. 客户端镜像生命周期与两端输入统一（2026-09-25）

> 对应 BACKLOG 的 `P0-5`（同维度重生后镜像永久失效）、`P0-6`（`evaluated` 无界增长）、
> `P0-7`（服务端入口仍读本端配置）。三条同属"客户端镜像与解析输入的生命周期"，一起改的。

### 现象

1. **重生之后客户端再也拿不到保护数据**。区域镜像（原型机保护范围 + 方块诞生周期）由整表快照建立，
   而快照只在**登录**与**换维度**时下发；客户端丢弃镜像的条件却是"{@code ClientLevel} 实例被替换"。
   两件事不重合——**同维度死亡重生**就会换一个 {@code ClientLevel}：镜像被清掉，却没有任何重发路径。
   后果是整局游戏客户端都不知道哪里受保护、哪些方块是玩家放置的：
   在被保护的立方体里照画幽灵（服务端根本不会转换），玩家放置的方块被当成世界原生方块。
2. **`evaluated` 负缓存无界增长**。它在每个编译过的位置被写入，但 `clearCache()` 开头是
   `if (targetCache.isEmpty() && activeSections.isEmpty()) return;`——而"`targetCache` 为空"
   恰恰是 {@code observerOnline = true}（失焦终止、不再产出幽灵）时的常态，断线也走同一路径。
   于是这张表在整个 JVM 会话里单调增长：每个编译过的区块节约 4096 条，键还是装箱的 `Long`。
3. **服务端入口与客户端入口读的不是同一份配置**。{@code MutationTargets.resolveServer} 走"读本端配置"
   的重载（`wild_chance`），`MutationPoolManager.protectionInfo` 读本端 `semantic_lock_stage3_strength`，
   `MutationIndexBuilder` 读本端 `wild_auto_include`；而客户端**只**吃同步下来的快照，
   且 `wild_auto_include` **根本不在快照里**。单人环境两者恰好相同所以从不暴露，
   局域网里客户端改过自己的 toml 就会分叉——与 §13.12 修过的是同一类，只是漏了这三个量。
   另外 `MutationSettings` 只在登录/换维度发，仓库内**没有 `ModConfigEvent` 监听**。

### 根因

三条各自的直接原因不同，但结构性原因是同一个：**"什么会让客户端的镜像/判定失效"这件事，
没有统一的落点**。丢弃判据散在 tick 里（换 level / 换 index / 换周期 / 换快照），
而"失效之后谁来补"只有登录与换维度两条路；配置的取值也散成"服务端读配置、客户端读快照"两条路。

### 修法

**`P0-6` —— 把"要不要重编译"与"要不要丢弃判定"分开**（最小、最直接）：

- `clearCache()` 不再提前 return：清表（`targetCache` / `evaluated` / `activeSections` / `sectionCounts`）
  **无条件做**，只有"标脏重编译"在确实没有幽灵时跳过（那本来就是纯开销）。
- 可以无条件清而不心疼：`clearCache` 的调用点全是低频事件（tick 里的周期/世界/查表变化、
  区域数据与快照更新），不在逐方块路径上；重建判定的代价在下一轮表面扫描里摊开，而那本来就是要做的工作。
- 周期日志加一格 `N cached decisions`（负缓存清空前的条目数），用来盯住这类增长。

**`P0-5` —— 服务端事件与客户端自愈互为兜底**：

- 服务端：新增 `MutationEventHandler.onPlayerRespawn`，**延迟 40 tick** 后补发区域与世界数据。
  延迟是必要的：立即发会被客户端随后的"换 level 清镜像"再清一次，等于白发。
- 客户端：tick 里发现"本维度没有整表快照"就主动请求。新增 C→S 包 `RequestRegionDataPacket`
  （无字段，服务端只回给请求者）。**这条更根本**：它把判据放在"客户端发现自己的数据没了"这个
  **事实**上，而不是"服务端认为客户端该要数据了"这个**推断**上——以后任何新的丢镜像原因都被同一条逻辑覆盖。
  请求前等 20 tick 避开登录时本来就有的那次推送；仍拿不到则每 100 tick 重试并打一条 ASCII 警告。
- `ClientRegionData` 增加显式的**快照标记**（`snapshotReceived`）：不能靠 `byDimension.containsKey`
  代替——`applyPrototype` 在整表到达前就会为维度建一份空数据，于是"键在"不代表"整表到了"。
  标记在 `clear()` 里一起清，否则新世界会以为自己已经收到过快照、**永远不请求重发**。
- **协议版本 1 → 2**：加了包就要改，否则"客户端发一个服务端不认识的包"会以连接失败收场、原因埋在日志里。

**`P0-7` —— 服务端也统一到同一份快照**：

- `MutationSettings` 增加 `wildAutoInclude` 字段并进快照编解码；新增进程级缓存
  `MutationSettings.server(seed)` 与 `invalidateServerCache()`。
- `MutationTargets.resolveServer` 改走快照入口；`MutationPoolManager.protectionInfo` 增加
  `MutationSettings` 参数，语义锁定强度取自快照。
- `MutationIndexBuilder` 不再直接读配置：取值经 `MutationIndexes.wildAutoInclude()`，
  由服务端（`fromConfig`）与客户端（收到快照）各自设置，**变化时丢弃索引缓存**（它决定池成员）。
- 新增 `ModConfigHandler`：配置重载时丢弃服务端缓存、重建一次、把新快照重发给所有在线玩家。
- `MutationHelper` 那个"读本端配置"的重载**保留但标注为只给自测用**——`[sync]` 段需要
  "服务端按配置算一遍"来与"客户端按快照算一遍"逐位比对，那正是这条不变量的回归网。

### 验证

**已验证**：`compileJava` / `build -x test` 通过；`runServer` 正常启动（`Done (1.037s)!`）。
全部自动化自测 **0 FAIL**，含：
- `[sync]` 全部 11 行（快照往返 12 字段、新增的"字段确实被搬运"断言、原型机往返、
  两端入口 960 样本逐位一致、阶段/时钟一致、候选体训练、显示刻回报 3 项、出生周期闸门）
- `[selftest]` 13 行（确定性/不收敛/对称/状态迁移/含水/热路径/物品池 3 项）
- `[anchor]` / `[entity]` / `[ritual]` / `[recipe]` 2 项 / `[period]` 8 项 / `[mutation]` 池审计

**新增断言本身也返工过一次，而且它先抓住了自己**：为了盯住"手写编解码漏搬字段"这个盲区
（漏搬时两端都落到默认值，`equals` 依然成立），我写了一条"翻转 `wild_auto_include`
看线上长度变不变"的断言——它 **FAIL 了**，因为 `writeBoolean` 无论真假都只写 1 字节，长度恒等。
改成"翻转后**解码结果**是否跟着变"才是正确判据。

**未验证**：
- **客户端实机**：`P0-5` 与 `P0-6` 都在客户端侧，需要真人游玩确认。具体要看的：
  死亡重生后站在基地保护区内应**无幽灵**；长时挂机后周期日志里的 `N cached decisions` 应保持有界。
  这两项已进 `P0-8` 的实机矩阵。
- **`P0-7` 的重载路径**：`ModConfigHandler` 需要运行期真的触发一次配置重载才能实测；
  自动化跑里没有触发点，目前只有编译与"不崩在构造期"的验证。
  （顺带记一个坑：`ModConfigEvent` 是 **mod bus** 事件，挂到公共 NeoForge 总线会在
  **模组构造阶段**直接抛异常导致整个模组加载失败——不是"功能不生效"那种温和失败。）
- 协议版本升到 2 之后的**跨版本联机**（新客户端 + 旧服务端）没有实测，预期是被连接期校验挡下。

## G. 一批独立小缺陷（2026-09-25）

> 对应 BACKLOG `P1-6` 的 16 个子项，本次处理了 7 项（3/4/5/6/8/9/15）。
> 其余 9 项仍在 BACKLOG 里，逐项标注了未做的原因。

### 现象

七条互相独立、但都属于"平时看不出来、出事时很难查"的类型：

3. `pendingSections`（还要扫哪些区块节）换世界时没清——它只在排空后才重建，
   所以换世界后会真的去扫上一个世界的坐标。
4. `activeSections` 出现**幻影条目**，导致多余的重编译：`incrSection`/`decrSection`
   都是"改计数 → 再改集合"两步，而三处调用者（主线程扫描、编译线程、`clearCache`）会交错。
5. `getPrototypeEffects()` 把内部那张**可变**列表直接交出去，调用方会长期持有它。
6. `syncedEffects`（"客户端现在以为的样子"）只增不减——被爆炸/活塞/`/setblock` 移除的基座
   不走 `BreakEvent`，留下的条目永不清理。
8. `totalStabilityRadius` 在 int 里算三角数，越界的 `copies` 会溢出。
9. `FocalDecayWorldData.partialTicks++` 不 `setDirty()`，崩溃最多丢 20 分钟的游戏日进度。
15. 右键的取消结果可以被**更晚**注册的 `receiveCanceled=true` 监听器翻转，
    而本模组无法察觉（于是原版可能拿旧 blockstate 再跑一遍交互）。

### 根因

七条的根因各不相同，但**第 8 条的根因值得单独说**：它反映了一种"靠下游兜底"的习惯——
`Math.max(PROTOTYPE_RADIUS, lost)` 确实把"半径变负数"这一种后果挡住了，
于是问题看起来已经解决。但半径会被当作**固化循环的边界**使用，
而"下游恰好兜住了"不等于"这里算对了"：换一种输入（或换一个调用点）就会漏出去。

### 修法

3. 换世界与断线时一并清扫描队列。
4. `incrSection`/`decrSection` 的复合更新放进同一个 `synchronized` 块，
   `clearCache` 也拿同一把锁——要的就是"两个集合看到同一个状态"，这是原子块能表达、
   无锁结构很难表达的东西。锁只在低频路径上（周期翻页/换世界/换查表/区域数据更新），
   逐方块路径一次都不会碰。
5. `getPrototypeEffects()` 返回**缓存的不可变视图**，内部改动后置空重建。
   不能每次 `List.copyOf`：`convertPrototypeRange` 会在逐坐标循环里调
   `protectionInfo`/`getGuidedBias`，而那两处要遍历这份列表——27 万次复制不可接受。
6. `syncRemoval` 里顺手 `pruneSyncedEffects()`：把"有效中心集合"与 `syncedEffects` 对账。
   判据是精确的——这张表描述"客户端现在以为的样子"，一个中心只要不在有效列表里就不该在表里。
8. 两层独立防护：算术改用 `long`（不可能溢出），返回值再夹进 `[基础半径, 32]`。
   另外给 `ObserverModelData` 加**规范化构造器**，把 `copies` / `progress` / `bioEnergy` /
   `stabilityStrength` 钳进合法域，列表字段做成不可变副本。
   上限取 1024 而不是"配置里的 `total_stability_max_copies`"：
   配置是**玩法约束**，而这里是**数据合法性约束**，两者不该耦合
   （整合包把玩法上限调到 16 时，这里也不该悄悄改写它读到的值）。
9. 每 tick `setDirty()`。写入成本几乎为零（原版按间隔刷盘），丢一整天进度的代价远大于它。
   **调试时钟刻意仍然不落盘**——那是"忘了 reset 会让世界看起来卡住"的测试档位。
15. 加一条诊断：`setCancellationResult(FAIL)` 之后复查一次，
    发现被改掉就打一条 ASCII 警告（带上位置与两侧的值）。我们无法阻止别的模组这么做，
    但可以把它变成**可诊断**的——整合包里出现双重交互时先看这一行。

### 验证

**已验证**：`compileJava` / `build -x test` 通过；`runServer` 正常启动；
全部自动化自测 **0 FAIL**（含新增的两条）。

新增两条断言钉第 8 条的不变式：
```
[selftest] model data clamps out-of-range inputs (copies/progress/energy/strength/concept): PASS
[selftest] total stability radius stays within [base, 32] for extreme copies: PASS
```

**A/B（去掉钳制，期望 FAIL）**：
```
[selftest] model data clamps out-of-range inputs: FAIL copies=2147483647 progress=-7 energy=-3 strength=5.0
[selftest] total stability radius stays within [base, 32] for extreme copies: PASS   ← 注意这条仍是 PASS
```

第二条**在无钳制时依然 PASS**，这是**预期且值得记录**的：半径那处我加的是独立的
`long` 算术 + 夹取，它不依赖入参钳制。也就是说两层防护各自独立成立——
这正好说明"只修一处"是不够的，而两条断言各自守住一层。

**A/B 过程本身也有一个坑**：第一次尝试用"在精简构造器里提前 `return`"来制造回归，
编译直接报 `精简构造器不得包含返回语句`（Java 的硬限制）。
改用"把四行钳制换成自赋值"才得到有效的回归版本。

**未验证**：
- 第 4 条的并发修法无法用现有自测证明（需要真实的并发压力 + 长时运行）。
  真正的验收是长时挂机后不再出现多余重编译——已进 `P0-8` 矩阵。
- 第 15 条的诊断只有在**装了两个会取消右键的模组**时才会触发，无法在纯净环境验证。
- 第 9 条的收益（崩溃少丢进度）需要真的崩溃一次才能观测，属于"按设计正确"而非"实测正确"。

## H. 保护判定去掉热路径分配（2026-09-25）

> 对应 BACKLOG `P1-3`。本次做了三件（实体白名单的登记期解析、保护规则抽成纯函数、
> 客户端引导模型列表的缓存），**空间索引那一项仍未做**，理由写在 BACKLOG 里。

### 现象

1. **逐实体造字符串**：`DoomsdayHandler.isEntityProtected` 对**每个实体**都
   `BuiltInRegistries.ENTITY_TYPE.getKey(type).toString()`，再拿这个字符串去
   `effect.trainedEntities().contains(id)`——而那是 `List<String>`，命中判定是线性扫。
   这两件事都发生在"每阶段周期对每个实体"的路径上。
2. **逐方块重建列表**：`ClientRegionData.guidedModels()` 被 `ClientRenderCache.resolve` /
   `liveTarget` 在**每个方块**上调用，每次都新建一个 `ArrayList`，
   并对每个引导模型重做一次 `MutationIndexes.tagged(concept)`（字符串哈希查找）。
   而 `resolveGuidedModels()` 的注释写着"每次扫描一个区块节解析一次"——
   **注释与代码不一致**本身也是这条缺陷的一部分：它让"这里很便宜"变成了没人再检查的假设。
3. **重复的半径判定**：`PrototypeEffect` 上没有半径方法，`MutationPoolManager` 里另有一个私有
   `withinRadius(pos, effect)` 助手——同一个规则两份实现。

### 根因

方块那一半早就修过（`Set<Block> trained`，见 §13.7 的三条性能问题），**实体那一半漏了**：
同样是"训练列表 → 判定集合"，只补了方块。另外两件（客户端缓存、重复判定）是
"注释描述了意图、代码没有实现"的积累。

### 修法

1. `PrototypeEffect` 增加 `Set<EntityType<?>> trainedEntities`，由新增的
   `parseTrainedEntities(...)` 在<b>登记期</b>解析一次。非法/已移除的 ID 一律忽略
   （训练期可能记下后来被移除的类型，那种条目就该不生效而不是抛异常）。
2. 判定规则收进 `PrototypeEffect#protectsEntity(EntityType, boolean bioStabilizesEntities)`
   ——一个<b>纯函数</b>。收在这里而不是留在调用方的循环里：判定规则与效果数据是一件事，
   散在调用方意味着"加一种型号就要改一处循环"。
   - 配置开关（`bio_stabilize_entities`）由调用方传入而不是在里面读，方法才与配置无关、可直接测。
   - **它不属于"两端必须一致"那类输入**：实体突变只发生在服务端，客户端不参与这个决策
     （与 `MutationSettings` 里那些会影响失焦<b>解析</b>的量不同）。所以服务端读配置是对的，只是读一次就够。
3. `ClientRegionData` 增加 `regionVersion`（任何写入 +1）与引导模型列表缓存；
   失效判据是**版本 + 维度键两个**。
4. `DoomsdayHandler` 增加"没有基座"的快路径（绝大多数世界在这一条上就返回了），
   半径判定改用 `PrototypeEffect#withinRadius`；删掉 Manager 里的重复助手。

### 验证

**已验证**：`compileJava` / `build -x test` 通过；`runServer` 正常；全部自测 **0 FAIL**。
新增两条断言：
```
[selftest] entity protection rules per model type
           (total / bio on+off / bio drained / lock trained+untrained / guided): PASS
[selftest] prototype radius uses Chebyshev distance (inclusive boundary): PASS
```
保护规则那条逐型号走了一遍，含两个容易写反的边界：生物稳定模型的"能量为 0 即失效"、
语义锁定"只护住被训练的**那几种**实体"。半径那条验的是切比雪夫距离与闭区间边界
（`距 4` 在内、`距 5` 在外、三个轴都吃半径）。

**A/B（把语义锁定改成恒 false，模拟"实体白名单没搬过来"）**：
```
entity protection rules per model type: FAIL
prototype radius uses Chebyshev distance: PASS
```
成立——这条断言确实能抓住"实体那半没接上"。

**未验证**：
- **本次修的是分配与重复，不是复杂度**：`protectionInfo` / `getGuidedBias` 仍然是
  线性扫全部原型机。在基座很少时这没差别，所以"没有回退"这件事我用**断言与行为等价性**来保证，
  而不是用基准数字——原有热路径基准在本次改动前后一致（实测 `chance=1.00` 34 ns /
  `chance=0.01` 151 ns，与本轮之前几次运行的 33~37 ns / 154~155 ns 在运行间波动范围内），
  但**它测的是方块解析，不覆盖这两条路径**。要有数字就得给它们单独加微基准，
  那属于空间索引那一项的工作。
- 客户端缓存的收益无法在无头服务器上量测（需要真实客户端跑扫描）。逻辑正确性靠
  "版本 + 维度"双判据 + `[sync]` 的两端一致性断言间接保证；实机看 `N cached decisions` 日志是否稳定。
- 客户端缓存的失效路径（增量到达 → 版本推进 → 下次查询重建）没有专门的断言。
  它是纯数据流，风险低，但如果将来出现"引导模型改了但预览没变"，先查这里。

## I. 编译线程上的 check-then-act 竞态（2026-09-25）

> 对应 BACKLOG `P1-4`（已从 BACKLOG 删除）。目标只有一件事：
> **让"这次查询属于哪个维度"变成显式数据流，而不是让每个查询各自去全局找一个可变字段。**

### 现象

`ClientRegionData` 的三个查询方法各自这样取维度：

```java
Minecraft mc = Minecraft.getInstance();
if (mc.level == null) return null;
return byDimension.get(mc.level.dimension());   // ← 第二次读 mc.level
```

`hasSnapshotForCurrentLevel()` 与 `guidedModels()` 是同一个形状。这类方法会被**区块编译线程**
（ForkJoinPool worker）调用——`ClientRenderCache.resolve` / `ghostState` / `computeTarget` 链上都会到。
于是主线程在两次读之间换世界或断线时：轻则读到错维度（拿到别的世界的保护数据），
重则第二次读返回 null 直接在 worker 上 NPE。

### 根因

`Minecraft.level` **不是 volatile**，而这三处都在做 `check-then-act`。
更根本的是**数据流方向错了**：调用方明明知道自己在处理哪个世界
（`resolve` 手里就有本次编译那个 `RenderChunkRegion` 的 `ClientLevel`），
却让被调用方回头去全局变量里猜。这正是"全局可变状态 + 隐式依赖"会必然产生的缺陷。

### 修法

1. `ClientRegionData` 的查询全部**接收维度参数**：`protectionInfo` / `isProtected` /
   `blockBirthPeriod` / `guidedModels` / `hasSnapshot`。它不再持有或读取任何全局状态。
2. `ClientRenderCache` 增加 `volatile ResourceKey<Level> currentDimension`，
   在 `tick()` 里随 level 一起发布（换世界时赋值，断线时置 null）。
3. **编译路径更精确**：`resolve()` 把 region/level 的校验**提到最前面**，
   于是 `clientLevel` 成为本次调用钉住的实例——保护查询、挖掘判定、`computeTarget` 内部的
   `protectionInfo` / `blockBirthPeriod` 全用它自己的维度，完全不碰全局字段。
   顺带一个好处：外来世界（`clientLevel != this.level`）在更早的地方就返回了。
4. 扫描路径与交互路径传入 `currentDimension`。

换世界时会有一个 tick 的窗口里 `currentDimension` 还是旧维度——但此刻 `byDimension` 已被清空、
新维度的快照也还没到，两个方向的查询都只会得到"没有数据"，也就是
**"不保护、无幽灵预览"这个安全结果**。这个窗口不引入新的错误状态，只是延迟。

### 验证

**已验证**：`compileJava` / `build -x test` 通过；`runServer` 正常；全部自测 **0 FAIL**
（`[sync]` 12 字段往返、`[selftest]` 含实体保护规则、`[anchor]`、`[entity]`、
`[ritual]`、`[recipe]`、`[period]`、池审计）。全仓扫描确认**没有残留的旧签名调用**。
顺手清掉 `ClientRegionData` 里因本次改动而不再使用的 `Minecraft` import。

**未验证（诚实说明）**：
- **竞态本身没有自动化断言**。它需要"主线程换世界"与"worker 线程查询"精确交错，
  而现有自测都跑在服务端主线程上，构造不出这个交错。
  本次能保证的是<b>结构上不再有 check-then-act</b>——`ClientRegionData` 里已经没有任何
  全局字段读取，`currentDimension` 是 volatile、单次读取。
  真正的验收是长时游玩（反复换维度/重生）不再出现 `ClientRegionData` 相关的
  worker 崩溃或"幽灵画错"——已进 `P0-8` 矩阵。
- 客户端行为（编译产物是否完全一致）没有实机比对。改动是纯数据流重构，
  两端一致性的回归网 `[sync]` 全绿。

### 留下的规矩

`AGENTS.md` §3.3 早就写着"从 worker 线程读主线程字段要一次性拿到（不要 check-then-act）"，
并点名了 `ClientRegionData.current()`。这次把它落实了，同时把**数据流方向**这条也写进守则：
**调用方知道自己处理的是哪个世界，就把维度/世界当参数传下去，不要让被调用方回头猜。**

## J. 开发环境与行尾统一（2026-09-25）

> 这不是缺陷修复，是一次**环境与仓库卫生**的整理。记下来的理由是：
> 本次为此花了真实的时间，而踩的坑都不是"难"，而是"没人写过"。

### 现象

1. **shell 环境变了**：原先只能走 PowerShell（Git Bash 起不来、WSL 无发行版），
   后来 Git Bash 可用（bash 5.3.15，`LANG=C.UTF-8`）。
   守则 §3.1 里那套"只能用 PowerShell + 显式处理 GBK"的写法因此过时。
2. **行尾混杂**：`core.autocrlf=true`，而 `.gitattributes` 只给 `src/generated` 下了 `eol=lf`，
   于是绝大多数文件在检出时被换成 CRLF、提交回 LF。
   多个工具（javac / gradle / git 的 `LF will be replaced by CRLF` 提示）都在刷噪音。

### 根因（行尾部分）

`core.autocrlf=true` 对**没有显式 `eol` 属性**的文件做"检出转 CRLF、提交转 LF"。
仓库里的 blob 一直是 LF（所以提交历史是干净的），但**工作区**是 CRLF。
缺的不是"配置错了"，而是"没给这些扩展名写规则"。

### 修法

1. `.gitattributes` 重写为**扩展名白名单**：
   文本扩展名 + `gradlew` + `.gitignore` + `.gitattributes` → `eol=lf`；
   `gradlew.bat` → `eol=crlf`（LF 会让 cmd 解析出错）；
   `.png`/`.nbt`/`.jar`/`.ogg`/`.zip`/`.dat` → `-text`。
   **刻意不用 `* text=auto`**：它靠"前 8000 字节有没有 NUL"猜，
   而本仓库有 `.nbt` 这种"看着像文本、其实是二进制"的格式，猜错会在行尾转换里改坏文件。
   （已有证据支持这个谨慎：`git diff --cached --stat` 显示重归一化**只动了 `.gitattributes` 一个文件**，
   二进制零改动。）
2. `git add --renormalize .` + 删除工作区文件后 `git checkout -- .`（全部已提交，无丢失风险）。
   结果：**351 LF / 3 CRLF**，剩下的 3 个正是两个 LICENSE（外部文本，不在白名单）
   与 `gradlew.bat`（特意 CRLF）。
3. 守则 §3.1 改写为"Git Bash 首选 + 编码与行尾硬规则表"；§3.3 / §6 / §8 同步更新。
   `PITFALLS.md` §1.4 补上四条坑（见下）。

### 验证

**已验证**：`gradlew.bat` 是 `DOS batch file, ASCII text, with CRLF line terminators`；
`gradlew` 是 `POSIX shell script, UTF-8 text executable`；二进制与 HEAD 无差异；
`git check-attr` 对 `*.java`/`*.md` 报 `eol: lf`、对 `*.png` 报 `text: unset`、对 `gradlew.bat` 报 `eol: crlf`；
行尾归一化后 `compileJava` 与 `build -x test` 均通过。

**未验证**：Windows 上 cmd 双击 `gradlew.bat` 的实际行为（只验证了文件属性正确）。

### 本次踩到的四个坑（都已写进 `PITFALLS.md` §1.4）

1. **`git checkout -- .` 会覆盖未暂存的改动**。我刚写完 `.gitattributes` 就跑了一次它
   （目的只是想刷新工作区），改动被静默冲掉——随后半小时都在查"为什么属性不生效"。
2. **属性是从索引/HEAD 读的**。`.gitattributes` 在工作区改好但没 `git add`，
   `git check-attr` 一律回 `unspecified`。这一条与上一条叠加，造成了最误导的现象：
   文件看起来"已经是新的"，git 却完全看不见它。
3. **嵌套 heredoc 的定界符不能重名**。外层用 `PYEOF`、内层也用 `PYEOF`，
   外层被提前结束，python 报 `unterminated triple-quoted string literal`，
   而 bash 随后又对着半个脚本报语法错——两层的报错都指向错误的地方。
4. **PowerShell 写文件带 BOM**。`Set-Content -Encoding UTF8` 写出 `EF BB BF`，
   javac 报 `非法字符: U+FEFF`。改用 `UTF8Encoding(false)`。

> 值得一提：第 1、2 条合起来正好印证了本项目反复出现的那个模式——
> **"看起来对"不等于"是那样"**。我当时的确"看到了新内容的文件"，
> 但 git 读的是另一个地方。这和之前"测试看起来 PASS 其实是空断言"是同一种错误。

## K. 挖掘路径重构（2026-09-25）

**状态**：已修 + A/B 验证（3 次）；客户端侧与整合包兼容性待实机（并入 `P0-8`）。
**BACKLOG 条目**：`P0-4`（已关闭）、`P1-6` 第 16 条（同源，已关闭）、`P1-6` 第 1、7 条（拍板保留现状）。

### 现象

生存模式挖掉一个已经失焦成别的东西的方块时，掉落**不是**你在看的那一块的掉落。

更深一层：同一件事在很多地方同时不对，而且每次"修好一个"都会冒出新的：

| 原版步骤 | 旧实现 | 玩家能看到的表现 |
|---|---|---|
| `playerWillDestroy` | 缺失 | 蜂巢不激怒、依赖它的模组方块状态不更新 |
| `onDestroyedByPlayer` | 缺失 | 拒绝破坏的方块被强行移除；水logged 方块的水一起消失 |
| `block.destroy` | 缺失 | NeoForge 的方块销毁钩子收不到 |
| `playerDestroy` | 缺失 | **自定义覆写的掉落全失效**——容器里的东西直接没了 |
| `spawnAfterBreak` | 缺失 | 红石矿额外掉落、sculk 等方块专属效果消失 |
| `BlockDropsEvent` | 缺失 | 其他模组改掉落/取消掉落全部失效 |
| `RULE_DOBLOCKDROPS` | 未检查 | 见下面"一条被推翻的判断" |
| `onPlayerDestroyItem` | 缺失 | 工具挖坏瞬间的模组钩子收不到事件 |
| `canHarvestBlock` 门控 | 部分 | 模组方块的自定义覆写被绕过 |
| `BlockEntity` 传给 `getDrops` | 传 `null` | 按方块实体算掉落的方块算错 |

### 根因

**不是"还差几个补调用"，是结构错了。**

旧实现在 `BlockEvent.BreakEvent` 里 `setCanceled(true)`，然后手工复刻原版
`ServerPlayerGameMode#destroyBlock` 的收尾（`setBlock(AIR)` → `Block.getDrops` → 自建 `ItemEntity`
→ `getExpDrop` → `mineBlock` → `awardStat` → `causeFoodExhaustion`）。

这条"手工管线"每补一条边就落后一次：原版加一步、别的模组加一个钩子，我们都得再补一次，
而且**没有办法验证"补全了没有"**——差集只能靠人工比对 NeoForge 补丁。

`BlockEvent.BreakEvent` 的公开 API 只有 `getPlayer()` / `setCanceled(boolean)`，
**改不了"被破坏的是哪个方块"**，而原版在事件触发之前就已经把 `blockstate1` 读进局部变量了。
所以唯一的出路是**动世界**。

### 修法

作者拍板选**推荐方案（重派发）**：只替换"被破坏的是哪个方块"这一个变量，让原版管线跑完。

```
BreakEvent(真实方块) 到达
  ↓ BREAK_REDISPATCHING 已置位？ → 是：什么都不做，让原版继续（这次面对的就是目标）
  ↓ 事件已被更早的监听器取消？ → 是：尊重它，什么都不做
  ↓ 校验锁定（位置 + 维度）→ 不通过：清掉，按原版处理
  ↓ setBlock(pos, targetState, 2)     ← 唯一改动世界的一步
  ↓ 清掉 BreakData                     ← 重派发会再次进入本方法，不清就会重复消费
  ↓ BREAK_REDISPATCHING = true
  ↓     player.gameMode.destroyBlock(pos)   ← 原版管线对着目标跑完整流程
  ↓ BREAK_REDISPATCHING = false
  ↓ event.setCanceled(true)            ← 真实方块那一次作废
```

于是上表**全部自动正确**，而且以后原版或别的模组新加的任何一步也自动正确。

**为什么不能"放进去然后不取消事件"**：原版已经抓着**旧** `blockstate1` 往下走了
（`playerWillDestroy` / `onDestroyedByPlayer` / `playerDestroy` 全用那个旧值），
改了世界也改不了它手里那份引用，结果会是"世界里的方块变了、掉落按旧方块算"——另一种不一致。

**`setBlock` 用 flag 2 而不是右键路径那个 flag 3**：这里紧接着就要把这块拆掉，
flag 3 会让邻块在几微秒内被通知两次（"变成目标"、"变成空气"），对红石之类是可见抖动。
方块形状没变，邻块本来就不需要为"这里换了种方块"重算。

**铜块碎片留在重派发之后单独结算**：那是本模组自己的语义掉落，不属于原版管线，没有管线可挂。

### 顺带修掉的三个 `BreakData` 缺陷

| 缺陷 | 修法 |
|---|---|
| 只校验 `pos`、**不校验维度** | 加 `dimension` 字段。`BlockPos` 只是三个整数，同一组坐标在下界与主世界都会相等 |
| `copyOnDeath()` 让锁定跨死亡存活 | **连序列化器一起删掉**（`ModAttachments` 只留 `builder`）。不可序列化 ⇒ 不落盘；不勾 `copyOnDeath` ⇒ 不跨死亡。两条路径一次性消失，而不是靠破坏时逐个校验去兜 |
| `getPeriodIndex()` 记了但从未读取 | 改为**诊断 + 明确不参与判定**，理由见下 |

**关于第三条，第一版做错了，A/B 推翻了它。** 第一版把"周期翻页"当成拒绝转换的理由
（`LockVerdict.STALE_PERIOD` → 清掉锁定、不转换）。写完之后重新推演语义才发现是反的：

- 锁定的语义是"**玩家看到的是哪个方块**"，它在挖掘开始那一刻定下来。
  玩家看着 A 挖下去就该拿到 A 的掉落——"看得见摸不着"正是这个模组要避免的事；
- 拒绝转换的后果是**静默不回退**：看着 A 挖、拿到 B 的掉落，比"按看到的给"更糟；
- 而且它触发得非常容易：调试时钟拨到高速时（`/focaldecay period speed`），
  一次普通挖掘就能跨过好几个周期。

所以周期现在只用于诊断，两条出口：跨周期时打一行 trace；`/focaldecay mutation at`
把整份锁定（位置 / 维度 / 周期 / 目标）连同当前显示刻一起打出来——
"挖出来的掉落和我看到的不一样"这类问题第一次有了可查的数字。
它不再是死数据，而且这两条出口回答的正是那个问题。

### 测试方块（作者批准注册）

`BreakProbeBlock` + 两个注册项 `focal_decay:break_probe_source` / `break_probe_target`：
无 `BlockItem`、不进创造栏、无配方。**没有 `BlockItem` 有一个我们要的副作用**——
`MutationIndex` 的池按 `asItem() != AIR` 过滤，所以测试方块不会被收进失焦候选、污染玩法
（审计输出里能看到它们出现在 "blocks with no item" 那一行，这是预期）。

探针把"原版调用了哪几个回调"变成整数计数，因为这件事用现成方块只能靠掉落间接推断，判据很脆。

### 验证

**已验证（自动化，`/focaldecay mutation selftest` 的 `[break]` 段，4 条断言全 PASS）**：

```
[break] lock validation (position / dimension; period must NOT invalidate): PASS
[break] vanilla pipeline runs on the VISIBLE TARGET (...): PASS
        [probe willDestroy=1 onDestroyedByPlayer=1 playerDestroy=1 spawnAfterBreak=1 dropsSpawned=1 diamonds=1]
[break] control: bare vanilla destroyBlock on the probe fires every callback: PASS
[break] doTileDrops=false suppresses output: PASS diamonds=0 broken=true viaVanillaPipeline=true
```

**A/B（硬要求，3 次）**：

1. **正常路径**：`[break]` 四条全 PASS。
2. **打开 `AB_OLD_MANUAL_PIPELINE`（把手工管线放回去）**：核心断言 FAIL，
   一次报出 5 个子项（`playerWillDestroy` / `onDestroyedByPlayer` / `playerDestroy` 全为 0，
   掉落也没落在被破坏的那一格）；控制组仍 PASS（它不走这条路径——这正好证明控制组测的是探针本身）。
3. **删掉 `validateLock` 里的维度判断**：首条断言 FAIL
   （`wrong dimension accepted (the P0-4 collateral defect)`）。

`AB_OLD_MANUAL_PIPELINE` 是一个**只有系统属性才能打开**的开关
（`gradlew.bat runServer -Dfocaldecay.abOldBreakPipeline=true`），
它保留旧管线那份代码用于回归。之所以固化成开关而不是每次手工改回来：
手工改容易忘了恢复，而且以后重构时没法重跑。

> ⚠️ **踩到的坑：Gradle 的 `JavaExec` 不把命令行的 `-D` 传给 fork 出来的 JVM。**
> 第一次跑 A/B 时 `-Dfocaldecay.abOldBreakPipeline=true` 完全没生效——测试照常跑完、
> 日志里什么都没有、四条断言全 PASS，看起来像"把 bug 放回去也没事"。
> 修法是必须在 `build.gradle` 的 run 配置里显式转发一次。
> 这个坑的危险之处在于**它的表现和"实现其实是好的"一模一样**。

**A/B 抓出的三个测试缺陷**（都不是被测代码的问题）：

1. **防空跑守卫写得太窄**。`doTileDrops=false` 那条本来用"`playerDestroy` 被调用过"当守卫，
   可那正是被测的性质——旧管线下守卫失败（"pipeline did not run at all"）把真正的判据
   （`diamonds=0`，正确）盖掉了，回归网失去鉴别力。守卫现在只回答"这次破坏到底有没有发生"。
2. **断言之间没清现场**。控制组会破坏目标格，而它后面那条断言假设"目标探针还在原处"。
   第一版只在开头清了一次，正常路径下**碰巧通过**（被测代码恰好把现场恢复成了期望的样子），
   旧管线下才暴露。现在每条断言自己 `resetSite`。
3. **按位置圈范围数掉落是错的**。两格相距 3、搜索半径 3，两个盒子必然重叠，
   于是上一条留下的钻石被下一条数进去（实测 `diamonds=2`）。
   改成"破坏前记 UUID 集合、破坏后取差集"，位置歧义从几何上消失。

**一条被推翻的判断（重要）**：`REVIEW-break-path.md` 说旧实现"未检查
`GameRules.RULE_DOBLOCKDROPS` → `doTileDrops=false` 时照样掉东西"。
**A/B 证明这条判断是错的**：把旧管线放回去，`diamonds` 仍然是 0。
原因是 `Block.getDrops` 内部就走 `popResource`，而 `popResource` 自己门控了该规则
（原版 `Block#popResource(Level,BlockPos,ItemStack)`）。旧实现唯一会绕过它的写法是
自己 `new ItemEntity` + `addFreshEntity`——它没这么写。
所以这条断言现在守的**不是**"旧实现的一个 bug"，而是"重派发跑的确实是原版那个入口"。
审计阶段写下的差集表有一项是推测而非实测，这正是本项目要求"区分代码确认的 / 文档声称的 / 推测的"的原因。

**未验证（并入 `P0-8` 实机矩阵）**：

- 装有机器的模组方块（自定义 `playerDestroy` 覆写）破坏后行为正确；
- 潜影盒 / 箱子破坏后内容物正常溢出；
- 红石矿的额外掉落（`spawnAfterBreak`）；
- 创造模式破坏行为不变；
- **中途放弃挖掘**：方块留在世界里的状态符合预期（这是本方案唯一的可见副作用）；
- **重派发之后原版收尾的幂等性**：`handleBlockBreakAction` 在 `destroyBlock` 返回后
  还会跑自己的收尾（`destroyBlockProgress`、`isDestroyingBlock = false` 等）。
  核对结果是这些大多幂等或会被下次交互覆盖，但**没有实机确认**；
- 可疑方块清单（考古、特殊交互方块）。
- 客户端侧的"方块闪一下"观察：取消事件时原版会把 `state`（真实方块）回发给客户端，
  但世界此刻已是空气、`setBlock` 的更新紧随其后。**理论上不闪，未实测。**
- `/focaldecay mutation at` 新加的 `breakLock=` 那一行，只验证了**无玩家来源**的分支
  （devtest 从控制台跑，打印 `(no player source - run this as a player)`）。
  玩家分支要真人执行才走得到，**未实测**。

### 已接受的取向（作者 2026-09-25 拍板，写进手册）

1. **破坏会真的把目标方块写进世界**。作者原话的意思是：这些方块本来就已经在世界上了，
   放不放进去对玩家与设定都不重要。副作用（中途放弃留下变过的方块）明确接受。
2. **世界种子明文下发给客户端**（`P1-6` 第 1 条）：绕过 `/seed` 权限是"客户端自行解析"
   这条架构的既定代价。作者明确表示不必加盐规避，保留现状。
3. **未加载的区块不提供保护**（`P1-6` 第 7 条）：不补 `ChunkEvent.Unload`。现状可以。

### 规律性教训（已提到 `PITFALLS.md`）

- **不要手工复刻原版生命周期**：只替换"操作的是哪个对象"这个变量，然后让原版跑完。
- **A/B 必须真的让开关生效**：`-D` 不转发会让 A/B 以"看起来没问题"的方式失败。
- **差分断言要能报出"差在哪"**：把判据和守卫混在一起，会把正确答案盖成看不出原因的失败。
